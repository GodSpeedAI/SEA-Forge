## Numbered findings (each with personally-observed evidence)

**F1. Multiplexing decision is correct and verified against the server's actual loop.**
I read `crates/sea-forge-server/src/lib.rs:1274-1382` (`handle_connection`): it reads one request line, `await`s `dispatch_bounded` inline, sends exactly one response line via the single-writer channel, and only then loops; the comment at lib.rs:1404-1407 states "NDJSON replies carry no sequence number, so a client pairs them with requests positionally." The Go client matches: `conn.call` (client.go:166-202) holds the per-connection mutex across one write + one read, marks the connection dead on any failure, and the pool (MaxConns default 4) hands each connection to exactly one caller — a second request can never be sent before the first response is read. Subscriptions never use the pool: `subscriberPass` dials its own dedicated connection (subscribe.go:89-96). The client's `mutationVerbs` set (frame.go:95-110) is exactly the server's `requires_durable_locator` set (lib.rs:1450-1468) — 14 verbs, identical.

**F2. No blind re-send of mutations; recovery resolves through the authority's correlation store.**
