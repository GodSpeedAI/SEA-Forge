Question: does the existing kernel serialize every authoritative case writer with inventory reads and mutation-event publication, such that `case.list` plus `events.get_range` can establish a complete, case-addressable frontier? What is the smallest source-grounded future home for that capability without a second durable history?

## Source facts: inventory and cursor surfaces are separate

`CaseListResult` contains only `cases` and `unreadable`; `CaseSummary` has no event cursor or inventory frontier (`crates/sea-forge-server/src/sfwp/case_views.rs:130-153`). The production `Request::CaseList` handler directly calls the synchronous filesystem listing and serializes its DTO (`crates/sea-forge-server/src/lib.rs:2396-2397`). The list itself returns a default empty DTO if `read_dir(cases)` fails, flattens iterator errors, skips failed directory checks/non-UTF-8 names, and omits `NotFound` reads (`case_views.rs:310-355`, with `read_case` behavior at `:249-270`). The separate fail-closed source-options note proposes a Rust fallible path and Go rejection of the existing `unreadable` array, but explicitly does not solve concurrent inventory atomicity.

`events.get_range` accepts optional exact `from_cursor`/`to_cursor` and returns `Vec<EventFrame>`; its implementation reads all ledger entries, filters by append ordinal, applies the 500-frame cap, and returns only rows (`crates/sea-forge-server/src/lib.rs:2349-2361`; `crates/sea-forge-server/src/sfwp/events.rs:165-207`). It does not return an explicit head/frontier or completion marker. The range page cap therefore is not a source-side scan/memory bound (CW-12, `.agents/DEBT.md:655-667`; ledger materialization at `crates/sea-forge-ledger/src/types.rs:784-801`).

The kernel's one durable global event ledger is already owned by `ServerState`; `publish_event` appends and returns a real `EventFrame.cursor`, then broadcasts it (`crates/sea-forge-server/src/lib.rs:94-102,208-234`; event cursor comes from the ledger `entry_ulid` at `sfwp/events.rs:61-85`). The case inventory and event range do not currently share a response or capture fence. Go's `ListCases` also discards `Unreadable` and accepts a zero-value missing-array decode as empty (`apps/godspeed-casework-go/internal/adapters/sfwp/authority.go:69-88`; `frame.go:653-667`).

## Source facts: writer synchronization does not cover inventory

`ServerState.case_locks` is a keyed async mutex, documented for serialization of `case.advance`/`item.execute` and supervisor passes on a **single case** (`crates/sea-forge-server/src/lib.rs:77-86,348-360`). It is not a cell-wide mutation barrier and `CaseList` does not acquire it. The request-work control is a semaphore with capacity `max_concurrent_runs`, not a single-writer mutex (`lib.rs:91-100`); concurrent request handlers can proceed.

There are concrete writer/read interleavings outside those per-case locks:

1. `case.commit` runs `case_dispatch::submit` without acquiring `case_locks`. Its blocking mint path creates the case directory, writes `case.json` and `plan.json`, and appends the case-local `CaseCreated` event (`crates/sea-forge-server/src/lib.rs:2491-2546,2759-2789`; `crates/sea-forge-server/src/case_dispatch.rs:39-124`). Only after submit returns does `commit_plan` insert the in-memory liveness entry and attempt the global `case.submitted` append (`lib.rs:2788-2822`). That publication `Result` is discarded and the successful case response is still returned (`:2814-2828`, CW-14). Thus a committed case can lack the global cursor the proposed gateway frontier expects.
2. The `case.add_item`, `case.reopen`, `case.terminate`, and `human_task.complete` wrappers call `run_case_mutation` without acquiring the keyed case lock (`crates/sea-forge-server/src/sfwp/case_mutations.rs:195-355`). The shared helper runs the filesystem mutation on a blocking thread and asynchronously publishes collected events; publication failures are logged and consumed, not returned as mutation failure (`:147-193`). By contrast `advance` acquires the keyed lock around its mutation and publisher join (`:396-462`). This is a useful same-case ordering guarantee for advance/supervisor, but does not establish all-writer serialization.
3. The opt-in supervisor separately calls `case_views::list` to choose active cases, then starts passes; the later pass acquires the per-case lock (`crates/sea-forge-server/src/supervisor.rs:82-145`). The inventory read and resulting mutation are not one atomic operation.
4. Startup rebuilds the in-memory `cases` liveness cache from `case_views::list` (`crates/sea-forge-server/src/lib.rs:151-202`). That map is explicitly not disk authority and is not the retained snapshot history.

The case commit write path uses `sea_forge_case_runner::write_json`, which performs direct `fs::write` (`crates/sea-forge-case-runner/src/lib.rs:570-575`). Existing case operation writes use a temporary file and rename (`case_ops/mod.rs:63-68`), but no shared inventory lock surrounds those writes either. Separately, the CLI `plan_pipeline::run_plan_inner` accepts a root, creates case state, and writes case files directly (`crates/sea-forge-cli/src/plan_pipeline.rs:100-120,374-413,480-500`). The server's `.server.lock` prevents a second server process (`sea-forge-server/src/lib.rs:1094-1115,1192`); the inspected CLI writer path does not acquire that lock. Whether operators may run a direct CLI writer concurrently with the server is not established here. A process-local kernel barrier would not cover such writes unless the supported ownership boundary excludes them or they participate in the same cross-process coordination.

## Counterexamples to an inventory-plus-range frontier

The successful-commit ordering found in the prior recon is real and narrow: the committed case files/local event precede successful `case.submitted` publication. It closes the particular scenario “a successful creation is not materialized until after a frontier that already includes its submit event” (`case_dispatch.rs:82-124`; `lib.rs:2788-2822`). It does **not** make a separate case-list scan and range watermark atomic.

For example, a cold reader can list an empty directory, then a successful commit can materialize case A and append `case.submitted`, then the reader can observe a range tail that includes that event. If it treats that tail as its resume frontier, its inventory omitted A while the event that would reveal A is already at/before the frontier. The inverse ordering (read a frontier before inventory) avoids this one schedule only if the inventory is a coherent complete view and all writes participate in the observed event protocol; current case-list errors, in-place writes, dropped event publications, and uncoordinated writers invalidate those assumptions.

An existing case can also be read while its `case.json` is changing. Direct `fs::write` is not temp-file/rename; enumeration has no shared lock with that writer. The current list may classify a transient read/stat problem as absent, or omit a partial directory, while an unreadable DTO cannot represent every skipped error (`case_views.rs:249-270,310-355`). A second list or successful `case.commit` ordering cannot prove filesystem snapshot semantics. These are bounded source counterexamples, not a claim that every platform will reproduce a torn read.

Finally, a case mutation can durably update the case-local trace then fail its global event append. `run_case_mutation` consumes that publication failure, while `case.commit` likewise ignores `case.submitted` failure. Consequently, an event-ledger cursor is a real cursor only for rows that landed; successful mutation response or directory presence alone is not proof that its newest state has a published global event boundary (CW-14 and the mutation helper at `case_mutations.rs:159-177`).

## Minimal candidate architecture for root/operator adjudication

No current operation provides a complete inventory, exact global event fence, and per-case ready cursor atomically. The smallest candidate that reuses existing truth sources, rather than adding another event/history store, is:

1. Harden the existing kernel `case.list` source to return failure for any enumeration/record uncertainty that makes “complete inventory” unprovable; preserve absent `cases/` as empty only when the cell root itself is valid. The already-present `unreadable` IDs remain useful, but the Go consumer must treat any such ID or malformed/missing required arrays as incomplete. This matches the source-options document, pending its public error mapping decision.
2. Add a kernel-owned writer/capture barrier spanning **all** kernel case creation and mutation paths from before filesystem mutation through successful durable global event publication. A complete inventory/cursor capture must take the mutually exclusive side of that barrier, read inventory and the durable events ledger fence as one operation, and fail closed if any case lacks a trustworthy published event boundary. Existing `case_locks` and request semaphores are insufficient. Propagating publication failure or explicitly putting the affected case into unavailable/gap state is necessary; logging-and-continuing cannot yield a complete-ready baseline.
3. Reuse the single `events_ledger` and its entry ULIDs as cursor authority. The existing `CaseListResult` has no fence/per-case cursor, and `events.get_range` has no explicit head, so the boundary must become available through an existing call's reviewed contract or another separately approved interface. A kernel response could carry the exact captured frontier and enough per-case cursor associations for the gateway to capture each case against real event history; do not synthesize cursors from the list, case IDs, timestamps, or in-memory counters. Any DTO/verb change needs the normal spec/schema/API decision.
4. Keep immutable case snapshot retention in the existing Go projection `Store`/Relay (`apps/godspeed-casework-go/internal/projection/store.go:55-65,149-220`; `internal/server/relay.go:178-217`). Establish per-case readiness there only after a validated ordinary snapshot is retained at its real case cursor. On a missing/failed cursor or projection/publication gap, that case is unavailable until a new real boundary is captured; no empty or fabricated SSE boundary. This uses the existing projection store for derived captures, not a second durable truth store.

This candidate is not yet a complete design. If the supported cell can be mutated by separate CLI/direct filesystem processes, a process-local kernel gate is insufficient; root must either define/verify sole-writer ownership or require a shared cross-process lock. A compound response that carries frontier/case cursor associations expands the SFWP contract. Cold-start per-case cursor derivation may require scanning the durable events ledger; `events.get_range` currently materializes all rows per call, so bounded work remains open (CW-12). It is not established whether per-case ledger tails and global event frames can be reconciled cheaply or whether every case write is guaranteed a global event.

## Decisions still requiring operator review

- Is the server the only supported writer for a cell while live V4 is active? If not, what shared lock/API boundary coordinates CLI and external writers?
- Is a new cell-wide capture barrier acceptable given long-running mutations, and which exact mutation/publication intervals must hold it?
- Should the existing `case.list` contract gain a captured frontier and per-case cursor information, or should an existing range response be extended? Define cursor namespace and exact completeness semantics before approving either.
- What existing error class truthfully represents incomplete inventory or missing publication, or is a public error-contract revision required?
- What bounded event-ledger read strategy supports cold-start case cursor derivation without relying on the current full-ledger materialization?

Until these are settled, inventory-plus-range remains a best-effort discovery input, not proof of an atomic complete frontier. No public V4 readiness, case-empty success, or operator authorization follows from this recon.
