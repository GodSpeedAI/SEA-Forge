## Findings

1. **Submit write/publication sequence is accurate.** The mint blocking closure creates the case layout and stream, commits `case_plan`, writes initial `case.json` then `plan.json`, and records `CaseCreated` (`case_dispatch.rs:53-137`). Dispatch later appends activation/local trace before spawning an episode; the episode task holds its run permit while calling `execute_sandbox`, returns a `Completion`, and then exits (`:337-449`). The outer dispatch loop subsequently calls `record_completion_blocking` and writes `case.json` (`:160-175,303-324,476-493`). `submit` itself has no `publish_event` or notifier call. Only after `submit` returns does `commit_plan` update the in-memory map, await the optional bounded `notify_command`, attempt `case.submitted`, discard that append result, and return success (`lib.rs:2764-2828`).

   **Qualification on run-permit duration:** the note's phrase “run capacity through capability execution and settlement” is too broad if “settlement” means the durable `settlement_event`/case trace commit. In `case_dispatch::submit`, `_permit` is owned by the spawned episode task (`case_dispatch.rs:370-372`); that task returns after `execute_sandbox` yields a `SettlementEvent` and forms `Completion` (`:399-449`). The permit drops when that task ends, before the outer task later calls `record_completion_blocking` to commit settlement and rewrite `case.json` (`:160-175,478-493`). The permit does cover capability execution and construction of its settlement result; it does not span that later durable settlement-record write. Separately, protected request admission is held in `dispatch_bounded` until `dispatch_admitted` returns (`lib.rs:1716-1786`), and an already-admitted timeout returns a timeout response without cancelling that work (`:1946-1988`). Root should preserve these as distinct lifetimes.

2. **Advance lock, capability, settlement, and publication ordering are accurate.** The caller holds the supplied run permit while `advance` acquires its per-case keyed mutex, runs synchronous `advance_case` inside `run_case_mutation`, awaits its publisher drain, drops/prunes the lock, and only then drops the permit (`case_mutations.rs:389-461`). For sandbox actions, `advance_case` appends activation, calls the episode executor, commits the `settlement_event`, appends/notifies settlement and completion events, then writes `case.json` (`case_ops/advance.rs:289-370`). `append_notify` notifies only after the local runner append succeeds (`:81-97`). This serialization is limited to advance/supervisor passes; the other `_with` mutation wrappers and `commit_plan` do not acquire `case_locks` (`case_mutations.rs:195-342,389-461`; `lib.rs:2764-2828`).

3. **The four direct `_with` operation orderings are accurate.** Reopen and terminate append the local event and invoke the notifier before writing changed case state (`case_ops/mod.rs:164-177,225-238`). `propose_item_with` commits/materializes `plan.json`, then appends/notifies `PlanMutated` (`:283-303`). Human completion appends/notifies the completion and any derived events before saving terminal `case.json` on the close branch (`:364-421`). The corresponding server wrappers call `run_case_mutation` and do not acquire the advance keyed mutex (`case_mutations.rs:198-342`).

4. **Notifier and event-ledger behavior is accurate, with one omitted failure case.** `CaseEventNotifier` is `&mut dyn FnMut(&TraceEvent)` and returns no result (`case_ops/mod.rs:18`); the server callback enqueues a cloned event and ignores send failure (`case_mutations.rs:180-184`). The separate publisher appends the global event and logs/consumes append errors; the helper then awaits the publisher task before returning the blocking mutation result (`:159-192`). The note correctly records that the task's `JoinError` is also discarded: `let _ = publisher.await` at `:191`. However, it does not explicitly call out that this means a publisher task panic/join failure is swallowed too and may terminate draining early. Add that nuance in any later source-facts correction; do not revise this immutable note.

   The global path is otherwise correctly traced: `publish_event` runs ledger work on a blocking thread, returns failure before broadcast if append fails, and broadcasts only after a real appended `EventFrame` exists (`server/src/lib.rs:208-234`; `sfwp/events.rs:59-89`). `LedgerStream::append` takes its per-stream OS lock around tail verification, entry append+`sync_all`, and MMR save (`ledger/src/types.rs:701-722,990-1003,1013-1068,1071-1089`). This lock scopes one ledger append, not the relationship among case files, local case ledger, and global event ledger.

5. **Read overlap and bounded publication-error inventory are accurate.** `case.list` reads case directories/records without acquiring the case keyed mutex (`case_views.rs:310-356`); `get_horizon` separately reads case, plan, and case events (`:416-420`) and folds those records without a writer fence (`:447-503`). The indexed `publish_event` callsite search covers `run_case_mutation`, `commit_plan` (invalid reload and `case.submitted`), approval `decide`, `delegate_inner`, and `cancel_delegation`; the note distinguishes the non-case adjacent publishers and correctly identifies consumed append results at those inspected sites. No claim about arbitrary external filesystem actors or every unrelated writer is made.

## Verdict boundary

No material source-sequence error was found. The run-permit wording above needs care when the root relies on this artifact: submit's per-episode permit ends before the later durable settlement commit, while advance's supplied permit spans the full mutation and publication drain. The swallowed publisher-task join failure is a bounded omission, not grounds to treat the source-facts artifact as an atomicity proof. The artifact is approved only as a source-grounded inventory of the stated paths; it authorizes no locking extension, contract/schema change, runtime claim, or public V4 readiness.
