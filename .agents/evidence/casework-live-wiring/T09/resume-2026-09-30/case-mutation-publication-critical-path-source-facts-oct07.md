## Shared append and notifier mechanics

`CaseEventNotifier<'a>` is `&mut dyn FnMut(&TraceEvent)` and returns `()` (`crates/sea-forge-case-runner/src/case_ops/mod.rs:18`). The notification callback cannot synchronously report a publication/write error to the case operation. In `run_case_mutation`, callback implementation clones the event into an unbounded `mpsc` send and ignores send failure (`server/src/sfwp/case_mutations.rs:180-184`). `case_ops::*_with` and `advance_case` propagate errors from their own case-ledger/file operations before or after callback invocation; the notifier itself is not fallible at the call site.

The local append is not one atomic combined case-file transaction: `CaseRunner::commit_event` commits a typed record to the case LedgerStream, then appends and flushes a JSONL line, then adds it to the in-memory vector (`case-runner/src/lib.rs:84-101`). For direct `_with` operations, `append_case_event_with` similarly commits case ledger, appends JSONL, then calls notifier (`case_ops/mod.rs:89-130`). A later `case.json` write may follow that notification, as in reopen/terminate/human completion. Plan mutation commits and materializes `plan.json` before the `PlanMutated` local event and notifier (`case_ops/mod.rs:283-303`).

The SFWP global ledger is a separate `LedgerStream` (`ServerState.events_ledger`, `server/src/lib.rs:105-113`). `publish_event` moves blocking work to `spawn_blocking`, calls `sfwp::events::append_event`, then broadcasts only after durable append success (`lib.rs:208-234`; `sfwp/events.rs:59-89`). `append_event` calls `LedgerStream::append` (`events.rs:61-80`); `append` takes that stream's OS file lock and performs tail read/verification, entry append+`sync_all`, and derived MMR update before unlock (`ledger/src/types.rs:990-1068,694-723,1071-1089`). This is a per-ledger-append critical section; it is not held across capability execution, case file writes, or the full mutation. The server source comments explicitly say the events ledger's own flock serializes publishers and no Tokio mutex is held over fsync (`server/src/lib.rs:105-110`).

## Concurrent readers and usable existing boundaries

`case.list` enumerates directories and reads `case.json` without a case lock (`server/src/sfwp/case_views.rs:309-356`). `get_horizon` separately reads case, plan, and event files in sequence (`:417-420`) and folds the current readable prefix (`:447-503`). It has no shared transaction with the writers above. Therefore its three inputs can reflect different points in a concurrent mutation; `case.json` can also be read before a later write after an already-notified local event. `case.get_overview` similarly reads multiple records independently (prior source anchors: `case_views.rs:358+`; existing recon holds the fuller observation analysis).

Existing serialization that is directly visible is narrow: server advance/supervisor passes on the same case share one keyed async mutex, held around the entire advance operation, including its long episode callback and global publisher drain (`server/src/lib.rs:79-86,343-360`; `case_mutations.rs:423-461`). Case-op wrappers do not take this mutex, and submit/commit does not take it. The ledger OS lock protects each ledger append, not the relationship among a case file, local case ledger, and global events ledger. These statements describe current boundaries and do not recommend extending them.

## Publication failures found on relevant server paths

- Trace frames from `run_case_mutation`: each `publish_event` error is logged and consumed; the blocking operation's `Result` is returned after publisher drain anyway (`case_mutations.rs:159-192`).
- Successful submit: `case.submitted` append result ignored after dispatch, cache insertion, and optional notify hook (`lib.rs:2814-2828`). Invalid config reload additionally attempts `invalid_reload_error` and ignores failure (`:2773-2785`).
- Approval decision: after case-keyed approval resolution, global approved/rejected append is ignored before response (`lib.rs:3107-3124`). This is adjacent global publication, not a case-file notifier path.
- Other server global publishers from the source callsite search: `agent_run.delegated` and `agent_run.cancellation_requested` also discard append results (`lib.rs:3234-3246,3317-3327`); they are not case/plan/horizon writers in the critical paths analyzed here.
- In every case, `publish_event` itself returns an error for task panic/ledger append failure; it ignores only broadcast `SendError` after a successful durable append (`lib.rs:221-233`). The callers above decide whether to propagate or consume the returned error.
