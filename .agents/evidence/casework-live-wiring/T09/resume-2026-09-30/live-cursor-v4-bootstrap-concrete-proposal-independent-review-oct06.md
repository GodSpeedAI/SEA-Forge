# Independent review: Live cursor V4 bootstrap component proposal

Date: 2026-10-06  
Reviewed artifact: `live-cursor-v4-bootstrap-concrete-proposal-oct06.md`, SHA-256 `e02ab804d95bf9aeb02878c6057716be8c7d24f0863dd5efc100408f4368bcc1`.  
Disposition: **REJECT as a complete component implementation blueprint; preserve full V4, inventory, and frontier HOLD.** This is document-only review, not public contract or implementation approval.

## Supported scope and decisions

The proposal preserves the current ready response `{snapshot: ...}` and gives the empty-state a mutually exclusive bootstrap arm containing only `status`, actual capture timestamp, session perspective, and existing template options. It does not synthesize case/world IDs, cursor, revision, or history. It explicitly gates bootstrap success on the separately held fail-closed complete-empty inventory correction; it does not treat an empty template catalogue as proof of no cases. These are sound, clearly scoped component rules.

Its route analysis matches current code: `/api/world` is session-protected (`internal/server/server.go:135-141`); the existing world response has only `snapshot` (`:422-424`); cursor requests resolve stored history and enforce any case consistency (`:188-207`); otherwise explicit case selection or `NewestCaseID` produces a live snapshot, with current empty selection returning `EmptyWorld` (`:209-230`). Template listing is session-protected (`:139`) and mapped by `LiveSource.EntryOptions` through existing `case.entry_options` (`internal/server/server.go:259-266`; `internal/projection/live.go:210-239,295-301`). The proposed bootstrap wrapper/Go DTO correctly reuses `ActorPerspective` and `TemplateEntryOption` (`internal/contract/contract.go:50-55,141-147`).

The create path keeps preflight and governance: the UI currently creates `PROPOSE_CASE` with empty case/cursor only after preflight (`apps/godspeed-cognitive-ui/src/app/proposals.ts:60-80`); Go requires consequential kind, action, actor, role-offered action, and valid template/digest/params before the narrow staleness exception (`internal/intents/intents.go:118-163,178-196`); server middleware retains session, CSRF, rate limiting, session actor overwrite, and kernel perspective check (`internal/server/server.go:142-146,233-256`). The proposal correctly calls for the schema exception to be narrowly action-specific and preserves same-ID/body replay semantics without promising idempotency across gateway restart.

UI state outside `WorldHistory`, startup branching before `App`'s `initialState`, explicit no-template UI, one-at-a-time authenticated refresh, abort/disposal, no SSE while cursorless, and opening-only-after-real-snapshot are all appropriate. Current `SessionApp` loads history before mounting `App` (`apps/godspeed-cognitive-ui/src/main.tsx:65-110`), while `initialState` requires `nowRevision(history)` (`model/store.ts:12-18,44-49`); `App` attaches the stream for `history.caseId` (`app/App.tsx:97-104`). `TemplateDesignPanel` can render empty/loading/unavailable and preflight states (`ui/TemplateDesignPanel.tsx:20-65,105-147`), but proposal flow is currently coupled to main Store and focus callback (`app/proposals.ts:12-27,60-98`), so the proposed extraction is indeed a needed seam. The proposal properly holds V4 route/readiness, inventory, cursor/ID grammar, and frontier changes.

## Blocking compatibility gap: bootstrap template DTO is not mapped to the UI port type

The proposed wire/bootstrap `templates` use the canonical contract DTO: `TemplateParameter.type` and optional `default_value` (`.agents/reports/interface-contracts/typescript/types.ts:549-567`; Go equivalent `internal/contract/contract.go:130-147`). However, the `TemplateDesignPanel` and proposal controller consume the *different normalized app-port type*: `param_type`, required boolean, and `default` string (`apps/godspeed-cognitive-ui/src/ports/contract.ts:223-239`; `model/types.ts:409-424`). The existing HTTP adapter explicitly transforms canonical `type`/`default_value` into those port fields (`adapters/http/httpCaseworkAdapter.ts:451-473`).

The bootstrap proposal defines `WorldBootstrap.templates` as canonical `TemplateEntryOption[]` and then says to seed the shared proposal controller/panel with those options, but it does not specify that same canonical-to-port conversion or a typed mapping function. Those types are not structurally assignable, and directly supplying wire values leaves the panel's `param_type`/`default` reads absent. The omission affects requiredness/default rendering and may affect parameter behavior for number/boolean/enum templates. Its conformance matrix says the panel renders bootstrap options but does not test this field translation.

**Required:** specify one exact mapping boundary: validate the bootstrap's canonical wire DTO, then normalize each template/parameter using the same rules as `HttpCaseworkAdapter.getTemplates` before storing `ProposalState` or rendering `TemplateDesignPanel`. Include mapping tests for all parameter kinds, required/default/options values, and empty arrays. Keep the wire schema in canonical field names; do not silently change either existing DTO.

## Additional implementation-boundary precision needed

The proposal requires a runtime validator for the response union and ordinary snapshot, but supplies no exact validator boundary/source strategy or typed refusal result. It correctly notes that `getSnapshot` currently casts `body.snapshot` without validation (`httpCaseworkAdapter.ts:233-240`); the implementation plan should specify whether validation lives in an authored hand-written runtime parser or another already-approved source. Do not introduce a dependency without approval. Ensure the response arms reject both/neither and unknown fields, and validate the template DTO before normalization.

The proposal's retry rule for an ambiguous `PROPOSE_CASE` transport outcome says to preserve the same ID/body, while current `createProposalFlow.submit` creates `uuid()` inside each invocation (`app/proposals.ts:61-77`) and `ProposalState` has no stored pending intent (`model/types.ts:409-424`). It describes the required behavior and tests, but the exact owner/storage/reset boundary for a stable pending intent ID/body is missing. A later implementation must retain the same identity through retry only while the outcome is ambiguous, bind it to the unchanged template/params/digest, and require a conclusive outcome before a changed body gets a new ID. This is security/idempotency-sensitive enough to make the controller extraction contract explicit.

The proposal appropriately refuses to poll arbitrary errors as “not ready,” because no current error class is established for that state. Its fallback to unavailable/retry UI is honest but means successful commit is not guaranteed to auto-open when the gateway's bounded cursor wait returns empty. The actual handler calls `postMutationCursor(..., "")` (`internal/intents/intents.go:294-301`); `WaitForCaseAdvance` returns the newest **successfully retained/published** cursor or the last published value when wait ends (`internal/server/relay.go:178-217`), not a readiness proof. This distinction should be carried in UI tests and descriptions. No source evidence supports stronger ready/frontier claims.

## Contract/schema mapping and held gaps

The authored `world-response.schema.json` with mutually exclusive strict arms is a plausible document proposal, and the Go/TypeScript variant shapes are concrete enough for architecture discussion. It proposes adding conformance cases and a golden while explicitly avoiding generated files. The response is not currently generated from this schema: the visible HTTP adapter currently casts a `snapshot` wrapper and the existing conformance test enumerates individual schemas (`httpCaseworkAdapter.ts:233-240`; `.agents/reports/interface-contracts/tests/contract-conformance.test.ts:130-138`). The later implementation must wire the new schema into that authored conformance inventory and keep Go, canonical TypeScript, and the app-port normalization synchronized; no generated-source pipeline is identified here, so the proposal should not imply one exists.

The remaining holds are correctly disclosed: current inventory is infallible/fail-open (`crates/sea-forge-server/src/sfwp/case_views.rs:309-355`; handler directly serializes it at `crates/sea-forge-server/src/lib.rs:2396-2397`); Go ignores `unreadable` (`internal/adapters/sfwp/authority.go:69-88`); range has no frontier token and reads the complete ledger (`crates/sea-forge-server/src/sfwp/events.rs:165-207`, `sea-forge-ledger/src/types.rs:784-801`); and current global Store/SSE is not the proposed per-case readiness boundary (`internal/projection/store.go:149-220`; `internal/server/server.go:293-325`). A true `no_cases` claim and public response success therefore remain unavailable until their separate decisions/evidence exist.

## Verdict and next step

The proposal is careful about scope, auth, preflight, false-empty behavior, real-cursor readiness, and unsupported frontier claims. It is **not complete for component approval** because bootstrap template values are not mapped into the actual UI proposal/panel port shape; runtime validation and stable pending intent ownership also need precise boundaries. Preserve the proposal and this review; request a bounded revision with those contracts and tests specified. Do not approve bootstrap release, full V4, inventory semantics, frontier, or implementation from this review.
