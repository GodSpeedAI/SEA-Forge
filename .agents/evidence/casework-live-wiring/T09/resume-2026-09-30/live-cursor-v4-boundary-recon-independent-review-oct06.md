# Independent review: Live cursor V4 boundary recon

## Disposition

**Factual review: substantially supported, with one material coverage omission; do not mark the recon fully complete yet. V3 remains rejected for operator approval in `live-cursor-contract-v3-independent-review-oct05.md`; this review does not reverse that verdict or approve a V4 contract.

## Supported findings

- **Identity producers disagree with frozen schema.** `case_id()` delegates to `timestamped("case")`, which emits prefix, UTC timestamp, and random suffix separated by underscores (`crates/sea-forge-core/src/ids.rs:32-47`). The Go projection builds `WorldID` as `"world-" + facts.Overview.Ref`, copies case ID and cursor as-is (`apps/godspeed-casework-go/internal/projection/builder.go:99-104`), and the local adapter uses `world-${caseId}` (`apps/godspeed-cognitive-ui/src/adapters/local/localAdapter.ts:314-316`). The cited schema instead requires `ws-...-<epoch>.<10 digits>` and hyphenated lowercase case IDs (`.agents/reports/interface-contracts/schemas/cognitive-world.schema.json:19-32`). The recon's mismatch finding and instruction not to rewrite IDs silently are accurate.
- **UI create-case flow is cursorless and preserves preflight.** `proposals.ts` requires a passing preflight digest, sends `PROPOSE_CASE` with empty `case_id` and `client_cursor`, requires a returned case ID, then calls `focusCase` (`apps/godspeed-cognitive-ui/src/app/proposals.ts:60-92`). `loadAndFocusCase` loads history before dispatching `loadHistory` and focus (`:105-122`). Current `WorldHistory` initialization indexes its last revision (`apps/godspeed-cognitive-ui/src/model/store.ts:12-18,44-49`), and the no-focused-object `centerActions` branch returns no actions (`apps/godspeed-cognitive-ui/src/app/App.tsx:238-253`). These support the need for a precise bootstrap state/transition while retaining the current preflight/create route.
- **Inventory can fail open as empty.** Rust `case_views::list` returns a `CaseListResult`, not `Result`; `read_dir` failure returns default empty (`crates/sea-forge-server/src/sfwp/case_views.rs:309-317`), iterator errors are flattened, and unreadable/non-UTF8 metadata paths can be skipped (`:319-341`). Only oversized or unparsable present records become `unreadable` (`:258-270`). The request arm directly serializes that infallible value (`crates/sea-forge-server/src/lib.rs:2396-2397`). Go's `CaseListView` has slice fields with no required-field validation (`apps/godspeed-casework-go/internal/adapters/sfwp/frame.go:664-667`), and `ListCases` decodes then iterates `Cases` without checking `Unreadable` (`internal/adapters/sfwp/authority.go:69-87`); absent/null slices therefore become an apparently empty result. The recon's proposed smallest repair direction is properly framed as an option requiring root error-class/API decisions, not as current behavior.
- **Range cap is not a frontier/work bound.** `events.get_range` materializes `ledger.read_entries()` before filtering/limiting and returns only `{"events": ...}` (`crates/sea-forge-server/src/sfwp/events.rs:165-207`; `crates/sea-forge-server/src/lib.rs:2349-2361`). `LedgerStream::read_entries` loads all entries to a vector (`crates/sea-forge-ledger/src/types.rs:784-801`). The recon correctly distinguishes frame cap from ledger load/repeated scan cost and notes the missing explicit frontier token.
- **Successful commit publication ordering is narrow.** Case files are produced in `case_dispatch::submit` before the successful return, then the server inserts the in-memory case and publishes `case.submitted` (`crates/sea-forge-server/src/lib.rs:2788-2822`; `crates/sea-forge-case-runner/src/lib.rs:570-575`). This supports only the specific after-commit event ordering claimed by the recon, not atomic filesystem inventory, complete scans, or recovery guarantees.
- **Store/SSE do not provide proposed case readiness boundary.** Store is global and cursor ordered (`internal/projection/store.go:55-65`); `Append` broadcasts globally and `Subscribe` replays/registers under its lock (`:149-220`). The route has no selected case parameter and registers before returning a 200/hello (`internal/server/server.go:293-325`). The recon accurately says current code does not implement V3's per-case readiness/replay-registration/gap invalidation boundary.

## Material omission to repair in the recon

The note establishes the UI's cursorless `PROPOSE_CASE` producer but does not trace the matching Go consumer/guard. That exception is important to its requested create-case contract: `internal/intents/intents.go:154-163` explicitly exempts `PROPOSE_CASE` from the target-case staleness guard because the target does not exist and binds freshness to the kernel preflight digest; `:182-194` validates `template_ref`, `preflight_digest`, and `params`; and `:283-300` maps the payload to its kernel call. Add these exact consumer anchors and state that the empty ID/cursor exception exists in the Go handler, while the frozen intent schema still rejects the UI's empty values and omits `PROPOSE_CASE` from its action enum (`interaction-intents.schema.json:7-14,22-44,49-56`). This keeps the exception explicit without inferring broad schema validity.

The note should also state directly that the live `/api/world` branch uses explicit `case_id` or `NewestCaseID`, while `?cursor=` takes the historical path; its cited server anchors already support this (`internal/server/server.go:177-230`). This is a small completeness improvement to the requested minimal live/legacy variant inventory, not a reason to authorize a route change.

Remaining uncertainty is correctly named: the filesystem scan is not atomic with writers; `case.submitted` is not a complete-inventory watermark; global Store/SSE cannot offer per-case readiness as-is; and any fallible list result/error mapping or interface/schema change needs a separate decision. Do not infer a runtime proof, architecture approval, operator authorization, or public implementation release.
