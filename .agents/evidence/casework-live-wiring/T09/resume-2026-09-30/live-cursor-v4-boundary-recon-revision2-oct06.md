## Kernel, Go, and UI identity producers/consumers

The kernel case ID producer is `case_id()` → `timestamped("case")`, which emits the `case_<UTC timestamp>_<hex>` form (`crates/sea-forge-core/src/ids.rs:32-47`). The frozen Cognitive World schema requires case IDs matching `^case-[a-z0-9_.-]+$` (`.agents/reports/interface-contracts/schemas/cognitive-world.schema.json:24-27`). Existing IDs are copied through Go projection unchanged; no translation or re-keying is evidenced.

Go's ordinary projection sets `WorldID` to `"world-" + facts.Overview.Ref`, copies the case ID, and copies the supplied cursor (`apps/godspeed-casework-go/internal/projection/builder.go:99-104`). The local UI adapter also creates `world-${caseId}` (`apps/godspeed-cognitive-ui/src/adapters/local/localAdapter.ts:314-315`). The frozen world schema instead requires a `ws-...-<epoch>.<10 digits>` world ID and the hyphenated case pattern (`cognitive-world.schema.json:19-32`). Thus V3's claim that the existing deterministic `world_id` already embeds cursor syntax is factually wrong. A cursor suffix adjustment alone would not reconcile either actual ID producer with both schema patterns. Any mapping or grammar change remains a separate reviewed decision.

The current UI creates a case through the existing template/preflight journey. `submit` refuses without a passing preflight and digest, then constructs `PROPOSE_CASE` with `kind: CONSEQUENTIAL_CASE`, a selected template target, empty `case_id`, empty `client_cursor`, actor, and template/params/digest (`apps/godspeed-cognitive-ui/src/app/proposals.ts:60-78`). On success it requires the returned object ID and focuses that case (`:80-92`); `loadAndFocusCase` fetches case history before it installs history and focus (`:105-122`). The UI therefore has a cursorless create request because there is no prior case projection, followed by a history-loading step that currently expects an ordinary case snapshot. This is the actual producer behavior, not evidence of a bootstrap response or a ready-snapshot wait protocol.

The matching Go dispatcher behavior is narrow and explicit:

- The mutating-intent staleness guard runs only when the target case ID is nonempty and the action is not `PROPOSE_CASE`. Its code comment says the new case does not exist before the commit and freshness is instead bound to the kernel preflight-digest precondition (`apps/godspeed-casework-go/internal/intents/intents.go:154-163`). This is an implemented exception for this action, not a general exemption for empty case IDs or empty cursors.
- `Handler.validate` recognizes `PROPOSE_CASE` and requires nonempty `template_ref`, nonempty `preflight_digest`, and nonnil `params` object (`intents.go:178-196`). The later execution path coerces each supplied parameter to a scalar string and invokes `CommitCase` with the template reference and present expected preflight digest (`:282-300`). This is the current Go handler/kernel-call path; it does not establish that the frozen schema declares the request valid.
- After successful commit, the dispatcher waits for the new case's first observed cursor using `postMutationCursor(..., "")` (`intents.go:294-301`). The comment describes waiting for the commit's own first frame. This is not a proof of a complete inventory, atomic scan, stable frontier, or new bootstrap wire arm.

The frozen interaction-intents schema conflicts with this implemented request shape. It requires `case_id` and `client_cursor`; the case pattern rejects an empty string, and the cursor pattern requires decimal epoch plus exactly ten sequence digits (`.agents/reports/interface-contracts/schemas/interaction-intents.schema.json:7-15,49-56`). Its `action_name` enum omits `PROPOSE_CASE` (`:26-44`). Thus the current empty-ID/cursor exception and action are implemented in UI/Go but are not valid under this schema as written. This recon does not claim a JSON Schema validator is invoked by the HTTP handler, nor infer that runtime dispatch turns this schema mismatch into an HTTP rejection. Normative/schema validity and executable path are separate facts; recon alone authorizes no schema or handler change.

## Current `/api/world` live and historical selection

The current `handleWorld` authenticates the session perspective first (`apps/godspeed-casework-go/internal/server/server.go:177-187`). If `?cursor=` is present, it calls `Store.At` and renders the retained revision; an unknown/evicted cursor returns typed 404, and a simultaneously supplied `case_id` must match that revision (`:188-207`). This is the historical path.

Without `cursor`, the handler uses an explicit `case_id` when provided. If absent or empty, it calls `NewestCaseID`; an empty result returns HTTP 200 with `projection.EmptyWorld`, while errors return typed unavailable (`server.go:209-220`). A nonempty selected case goes to `world.Snapshot` at the relay's newest observed case cursor (`:222-230`). This is the live path. Explicit case requests do not redirect to another case. The current response arm is always `worldResponse{Snapshot: ...}` in these branches; no mutually exclusive bootstrap arm is implemented here. The empty-world success is a synthesized empty snapshot and does not by itself prove a complete-empty kernel inventory.

This branch description is the minimal actual behavior: explicit case → live snapshot; no case → newest live case or empty snapshot; cursor → retained historical snapshot, with optional case consistency check. It does not select a new V4 route policy or define what a future bootstrap variant should contain.

## Inventory completeness and error channel

Rust `CaseListResult` is currently a success DTO with `cases` and `unreadable` fields (`crates/sea-forge-server/src/sfwp/case_views.rs:143-153`). `case_views::list` returns an infallible value rather than `Result` (`:310-355`). A `read_dir(cases)` failure returns a default empty result (`:314-317`); iterator errors are flattened, metadata failures and non-UTF8 names are skipped (`:319-325`), and read/metadata failures mapped to `NotFound` are omitted from the list (`:249-270,336-341`). Only present records that fail parse/size validation are represented as unreadable. The `Request::CaseList` handler serializes this value directly (`crates/sea-forge-server/src/lib.rs:2396-2397`). Consequently the Rust path has no operational `Result` channel that distinguishes every enumeration failure from genuinely empty success.

Go `Authority.ListCases(ctx) ([]CaseRecord,error)` propagates transport/decode errors, but after decoding it iterates only `view.Cases`; it does not inspect `view.Unreadable`, and absent/null slices can appear as an empty zero-value view (`apps/godspeed-casework-go/internal/adapters/sfwp/authority.go:69-88`; `CaseListView` at `internal/adapters/sfwp/frame.go:664-667`). `NewestCaseID` treats an empty list as no cases (`internal/projection/live.go:173-189`), which the live handler currently turns into `EmptyWorld` HTTP 200 (`server.go:209-220`). Go-only strictness cannot recover omissions that Rust already collapsed.

The prior source-options note (`case-inventory-fail-closed-correction-source-options-oct06.md`) records the smallest no-wire-field correction considered: a Rust-internal fallible list path used by the production handler, strict Go required-array validation, and Go rejection through its existing error channel when `Unreadable` is nonempty. A valid absent or readable empty cases directory can remain successful empty; iterator failures must not be flattened; known unreadable case IDs should remain represented. A correct existing top-level error mapping still needs root decision, and a public error-class or Rust/Go interface change needs separate review. This is an option recorded for later adjudication, not a decision or approval in this recon.

The current filesystem inventory is not atomic with writers. `CaseRunner::write_json` uses direct `fs::write` (`crates/sea-forge-case-runner/src/lib.rs:570-575`); a successful scan cannot by itself prove a consistent point-in-time inventory or successful recovery from partial writes.

## Range/frontier and publication ordering

`events.get_range` accepts optional exact `from_cursor`, `to_cursor`, and `limit`, filters ledger entries by append ordinal with exclusive `from` and inclusive `to`, and caps returned events at 500 (`crates/sea-forge-server/src/sfwp/events.rs:165-207`). The kernel response is only `{events:[...]}` with no `done` or frontier member (`crates/sea-forge-server/src/lib.rs:2349-2361`). A short or empty page is not an explicit completeness frontier. The response count cap does not bound `LedgerStream::read_entries()` materialization or repeated scan cost (`crates/sea-forge-ledger/src/types.rs:784-801`).

The source recon `case-inventory-frontier-race-source-recon-oct06.md` establishes one narrow successful-commit ordering: case files and in-memory entry precede global `case.submitted` publication (`crates/sea-forge-server/src/lib.rs:2788-2822`; `crates/sea-forge-case-runner/src/lib.rs:570-575`). A future frontier that includes this event would close that particular successful-commit-after-frontier race, assuming ordinary filesystem visibility. It would not prove complete inventory, stable filesystem snapshot semantics, or recovery of failed/partial dispatch. `CaseCreated` is in the per-case ledger, not the global range ledger. No atomic head token or frontier can be inferred from the current range response under concurrent writes.

## Store/SSE boundary

The Go projection Store is global and stores revisions in cursor order (`apps/godspeed-casework-go/internal/projection/store.go:55-65`). `Append` compares cursors and broadcasts globally (`:149-190`); `Subscribe` selects replay and registers under the Store lock (`:193-220`). The current SSE route has no selected-case input, subscribes globally, and writes HTTP 200/hello before streaming (`apps/godspeed-casework-go/internal/server/server.go:293-325`). Those interfaces do not implement V3's proposed per-case unavailable-before-header behavior, case-scoped replay, or an atomic gap invalidation/cancellation boundary with subscriber registration. Current code must not be described as having V3/V4 readiness.

## Deviations from V3 and retained uncertainties

This revision retains the original recon's factual V3 corrections: actual kernel/Go/UI IDs contradict the frozen identity schema; the UI's cursorless creation request and Go consumer are real but the frozen intent schema does not make them normative-valid; current empty-world response is not a complete-inventory proof; inventory can fail open; range paging caps frames without bounding scan work or exposing a frontier; the successful-commit publication ordering is narrower than atomic inventory; and the global Store/SSE route does not provide per-case readiness. It adds the previously omitted Go `PROPOSE_CASE` stale-guard exception, typed payload requirements and existing CommitCase call, and makes explicit-case/newest live selection distinct from cursor-qualified historical lookup.

Still unknown or unproven: whether current HTTP dispatch performs any external schema validation (the cited handler path does not establish one); whether filesystem enumeration can provide a coherent snapshot under concurrent writes; whether successful commit ordering extends to failed/partial operations; how a reliable kernel inventory/frontier error should map to the top-level public response; how case-specific replay registration, gap invalidation and cancellation would be made atomic; and how IDs/world IDs/cursors should reconcile with frozen schemas. These require separate source investigation and root/operator decisions. Do not infer an atomic as-of-event snapshot, complete empty inventory, public cursor grammar change, or automatic readiness.
