## 2. Correction 1 — lossless wire ordinals

The ledger continues to own an unsigned 64-bit `append_ordinal`; it is never replaced by or inferred from its opaque `entry_ulid`. At present `LedgerEntry.append_ordinal` is `u64` (`crates/sea-forge-ledger/src/types.rs:191-207`), assigned while holding the stream lock (`:701-721,1000-1069`). `EventFrame` currently carries only the exact string cursor (`crates/sea-forge-server/src/sfwp/events.rs:15-31,61-83`), and `get_range` resolves cursors to ordinals only after `read_entries()` materializes the ledger (`:169-208`; `LedgerStream::read_entries`, `crates/sea-forge-ledger/src/types.rs:784-801`).

Every ordinal crossing JSON becomes a **canonical unsigned decimal string**, not a JSON number. This applies consistently to `EventFrame.append_ordinal`, range request `after_ordinal`/`through_ordinal`, page `head.append_ordinal`/`scanned_through_ordinal`, continuation ordinals, Go `KernelEvent`/`Revision`, `CognitiveWorldSnapshot.cursor_ordinal`, SSE hello/resync/snapshot envelope fields, and any other ordinal exposed by this candidate. Internally Rust and Go retain `u64`; serialization/parsing is an explicit checked adapter. Canonical grammar is `0|[1-9][0-9]*`: reject empty, signs, whitespace, leading zeros except `0`, decimal/exponent notation, and values above `18446744073709551615`. On-disk `append_ordinal` remains numeric as currently stored; this is a wire representation change only.

In TypeScript, the public contract type is a decimal-string alias, validated against that canonical grammar. Every ordering/comparison converts validated strings to `BigInt`; it never calls `Number`, uses lexicographic ordering, or silently narrows the domain to `Number.MAX_SAFE_INTEGER`. JSON Schema describes a string with the canonical decimal pattern; the hand-authored parser checks the upper `u64` bound without a lossy numeric conversion. Rust checked increment and Go checked parse return a typed ordinal-exhaustion/overflow failure; neither wraps nor fabricates the next ordinal. Ordinal/cursor disagreement remains an integrity failure. The exact `entry_ulid` stays the SSE `id`, history key, and `client_cursor`; clients do not supply an ordinal as authority.

This replaces only base §2’s JSON-safe-integer ordinal wire proposal. It adds the exact public ordinal string shape and overflow error semantics to the required SFWP, Go, TypeScript, and authored-schema changes. It does not alter ordering, identity, or frontier decisions.

## 3. Corrections 2 and 3 — bounded replay, live queue, and write authority

### Atomic admission returns distinct replay and live mechanisms

The existing Store is global and cursor-lexical (`apps/godspeed-casework-go/internal/projection/store.go:43-65,153-227`); `Subscribe` copies all selected replay revisions into a channel sized to `len(replay)+subscriberBuffer` while holding its mutex (`:196-227`). The current `/api/events` route authenticates, registers that subscription, writes `200` and hello, and only then checks whether the requested cursor predates retention (`apps/godspeed-casework-go/internal/server/server.go:293-376`). The candidate replaces those mechanics with a case-scoped preparation boundary; no claim is made that current code already provides it.

`PrepareCaseSubscription(caseID, lastCursor, lastCaptureDigest)` runs under the per-case Store mutex and, at one admission linearization point, checks readiness/gap state, resolves the exact cursor plus capture digest, takes a bounded **immutable replay snapshot**, accounts its canonical serialized bytes, and registers the subscriber for later live appends. It returns two separate objects: (a) the immutable replay slice, at most 64 revisions and 4 MiB of canonical snapshot/event bytes; and (b) a new fixed live queue with capacity at most two frames and 2 MiB. Replay frames are never inserted into the live queue. A store append serialized after admission can enter only that live queue, so replay precedes live delivery without a second unbounded channel.

If the requested cursor/digest is unknown, evicted, mismatched, or replay would exceed either replay bound, do not return a partial replay. Return a pre-header typed `resync_required` response naming only real retained cursor/ordinal/digest values, clear the client’s affected-case history, fetch the exact current capture, then subscribe from that boundary. If the retained boundary itself is unavailable, return typed unavailable. If subscriber-count or aggregate byte admission fails, reject before response headers; do not register a partial subscriber. The existing base limits (64 revisions/4 MiB per case, 64 MiB per-process Store retention, 128 case heads, 32 active streams, two live frames/2 MiB per live queue, 1 MiB maximum snapshot) remain proposals.

### Exact byte accounting and overflow

Maintain separate, mutex-protected counters for Store-retained canonical serialized snapshot bytes and subscription-owned canonical serialized bytes. Subscription bytes include every not-yet-written replay item, every queued live frame, and the one currently authorized/in-flight write until its write finishes or aborts. On dequeue, bytes move from queued to in-flight; they are not released at dequeue. Once a replay item has completed, clear its replay-slice slot and release its charge. On cancellation/cleanup, release all remaining replay, queue, and in-flight charges exactly once. Charge each subscriber’s retained copy conservatively even when immutable values share Go pointers.

Propose a 64 MiB process-wide subscription serialized-byte budget across all replay snapshots, live queues, and in-flight writes, in addition to the base 64 MiB Store-retention budget. Keep per-subscriber limits of 4 MiB replay, 2 MiB queued live data, and at most one in-flight event no larger than 1 MiB. Keep at most 32 active streams. If the aggregate budget cannot admit a replay or a live event would overflow its subscriber/process budget, mark that subscription as gapped and remove it from delivery under the mutex; after unlocking, signal its cancellation owner. A slow reader is terminated and must reconnect through the exact replay/resync boundary. Do not truncate frames, block append on a reader, or quietly drop one frame while claiming continuity.

These are limits on canonical serialized payload bytes plus bounded counts/slices, not a measured or exact heap/RSS ceiling. Go object overhead, allocator behavior, HTTP buffers, and kernel buffers are not inferred from JSON length. The explicit maximum connection count and queue/replay counts bound those structures; their actual resident memory remains a verification/measurement question. A final heap/RSS budget, if required, needs separate measurement and root/operator approval rather than a claim derived from these byte counters.

### Invalidation, dequeue, headers, and writes

Readiness/gap mutation and replay selection/registration use the same Store mutex. Invalidation wins under that mutex by marking the case unavailable, advancing its process-local generation, removing subscribers from future delivery, and detaching their cancel handles. It closes/cancels subscriber signals only after releasing the mutex. It does not synchronously perform network I/O, wait for a handler, or close a channel still reachable by a sender. A later accepted capture begins a fresh generation and real retained boundary; a delayed old-generation append/write is rejected.

The handler obtains a locked write permit for the admitted generation immediately before writing response headers/hello and before each replay or live frame. A live dequeue and its permit are one mutex-protected action; the handler then performs the network write outside the lock. Every permit checks that the case remains ready, the subscription generation still matches, the subscriber is registered and ungapped, and the next item is within its byte budget. If invalidation won before a permit, the handler writes no later header/frame. If a permit won first, its already-authorized write may race with later invalidation and finish afterward. This is the actual as-of linearization guarantee; it is **not instantaneous revocation**, not atomicity with kernel Facts, and not a promise that bytes already authorized or buffered can be retracted.

Use one network writer per response and a bounded write deadline for each header/frame operation. The store-side invalidation owner signals cancellation outside the mutex; the stream handler owns response writes, observes cancellation, stops obtaining permits, and releases its subscription accounting on exit. A blocked write can therefore delay cleanup only until its bounded deadline. At most one permitted write per connection can remain in flight after invalidation, with a serialized payload no larger than 1 MiB; no subsequent permit is issued. If the eventual HTTP stack cannot enforce bounded write cancellation, that is an implementation HOLD, not a reason to call network code under the Store mutex.

Unauthenticated, missing/duplicate/empty case, unavailable, gap, too-old/unknown cursor, digest mismatch, replay overflow, and budget rejection all resolve before `WriteHeader(200)`. A cancellation that wins after the locked header permit but before the actual network write may still race with that one permitted handshake; the response then terminates without any subsequent frame. This residual is disclosed rather than claiming lock-to-wire atomicity. Ordinary GET/Store capture availability and session auth are checked at their own documented boundaries; none of these locks makes filesystem inventory or `WorldSource.Facts` atomic.

These rules replace only base §5’s ambiguous replay-in-queue and subscription/write transition. They retain its exact case route, case-keyed ordinal Store, pre-header resync/error policy, SSE IDs, caps, gap invalidation, and “no network I/O/callback/cancel under Store lock” requirement.

## 4. Correction 4 — restart-safe capture identity without synthetic authority IDs

The exact pair `(cursor, cursor_ordinal)` identifies a durable ledger event, **not a unique UI capture**. `cursor` remains the opaque real `entry_ulid`; `cursor_ordinal` remains its lossless decimal-wire ordinal. Neither is regenerated or changed when Facts are recaptured. `world_id` remains stable `world-<exact case ID>` and is not capture identity.

Add an ordinary-snapshot `capture_digest` field, canonically encoded as `sha256:v1:<64 lowercase hex characters>`. It is derived from deterministic canonical UTF-8 JSON for the complete public `CognitiveWorldSnapshot` **with only `capture_digest` omitted from its own digest input**. The canonicalization version fixes UTF-8 handling, object-key ordering, number formatting, array order, and string escaping; use one versioned RFC 8785/JCS-compatible representation across Go and TypeScript verification fixtures. Do not hash private `Facts`, ledger bytes, event detail, access-control state, or an authority token. `timestamp`, stable IDs, exact cursor, decimal ordinal, perspective, and all other public snapshot fields are part of the bytes. Thus a new process baseline at the same real event cursor but captured at a new time is a distinct immutable capture even if other displayed values happen to match. Digest computation failure or noncanonical output prevents that capture from becoming ready.

Go `Revision`, JSON world snapshot, SSE snapshot payload, hello/current-boundary metadata, and `resync_required` payload carry the digest of the exact public capture. It is not an event ID, cursor, sequence, authorization credential, stale-intent authority, or a synthetic ledger record. It does not make a baseline a historical reconstruction and does not add a second history source.

For historical `GET /api/world?cursor=...`, require the exact `capture_digest` paired with that cursor. If the server cannot identify that capture in retained history or its digest differs, do not return a different snapshot that happens to share the cursor; return a typed pre-body resync/error naming only an actual current retained boundary. A current-world request with no historical cursor continues to return the current validated capture. For SSE, retain exact cursor in `id:` and use an explicit `last_capture_digest` query value paired with `last`; do not encode the digest into a fabricated cursor. The current HTTP adapter disables native automatic retries and reconnects itself (`apps/godspeed-cognitive-ui/src/adapters/http/httpCaseworkAdapter.ts:297-365,380-430`), so the proposal extends its reconnect state to carry the latest event’s cursor **and digest**. This avoids reliance on a browser-generated `Last-Event-ID` to carry information it cannot encode.

On process restart, the derived ledger head index may persist, but process-local capture history does not. Capture a new `process_baseline` at the latest verified real case cursor using actual current Facts and capture time; do not republish old client bytes as if they were available history. When a client presents the same `(caseID,cursor,ordinal)` with a prior digest and the newly retained capture has another digest, report resync to the real new capture. The UI clears only that case’s old history/caches and fetches the actual current snapshot. Matching digest means the canonical public capture bytes match; it does not prove source Facts were atomically read with the event or authorize a mutation.

This corrects the base’s missing cross-restart distinction. It adds a public snapshot field, a required digest for historical world lookups, an SSE reconnect query field, parser/schema/TypeScript changes, and client resync behavior. All require authored schema/API/ADR updates and exact operator approval. Missing digest on a historical cursor request is rejected/resynced; it is never silently treated as a match.
