## Live vocabulary and paths

The live Go gateway admits only `CONSEQUENTIAL_CASE` and names in `AllIntentKinds` (`apps/godspeed-casework-go/internal/intents/intents.go:118-128`; `apps/godspeed-casework-go/internal/contract/contract.go:372-386`). That ten-name set is `PROPOSE_CASE`, `ADD_DISCRETIONARY_WORK`, `EXECUTE_ITEM`, `COMPLETE_HUMAN_TASK`, `APPROVE_HUMAN_TASK`, `REJECT_HUMAN_TASK`, `ESCALATE_OR_OVERRIDE`, `OPEN_ARTIFACT`, `REOPEN_CASE`, and `TERMINATE_CASE`. It matches canonical `ConsequentialIntentName` (`.agents/reports/interface-contracts/typescript/types.ts:140-150`) and the T01 recorded intent set (`.agents/evidence/casework-live-wiring/T01/confirmation.md`, “Kind sets exact”). `ESCALATE_OR_OVERRIDE` is admitted by the vocabulary but explicitly returns `UNAVAILABLE` before a kernel route (`intents.go:259-262`); inclusion does not mean every action succeeds.

Production UI builds ordinary intents from offered action descriptors in `src/app/intents.ts:40-64`, including typed payload defaults for execute, complete, reopen, and terminate. It chooses `BACKEND_INFORMATION` for a non-consequential descriptor (`:53-56`), but the current Go handler rejects every kind except `CONSEQUENTIAL_CASE` (`intents.go:123-128`). Proposal submission is a separate live path: `src/app/proposals.ts:68-77` sends `PROPOSE_CASE` with `CONSEQUENTIAL_CASE`, empty `case_id` and `client_cursor`, and preflight-backed parameters. Go exempts that action from freshness checking because the destination case does not yet exist (`intents.go:154-160`) and validates its payload (`:182-196`). Thus the canonical nonempty case/cursor patterns exclude an actual creation envelope. The ordinary UI path reads the current history revision into `client_cursor` (`intents.ts:58-60`).

Exact-name search across the production UI, Go intent handler, and canonical files found no live `CREATE_CASE` or `ASK_PROTOCOL` action. `BEGIN_WORK` is in the legacy action vocabulary/type/schema only; it is not in Go `AllIntentKinds`. This distinguishes the separate Thoth Ask API/schema from `InteractionIntent.action_name`.

## Canonical source and drift

The UI imports `InteractionIntent` directly from the canonical authored TypeScript package (`apps/godspeed-cognitive-ui/src/ports/contract.ts:11-40`), so `types.ts` is source-current for this UI boundary; Go declares that its contract mirrors the same canonical TypeScript source (`internal/contract/contract.go:372-374`). The union at `types.ts:114-155` includes both older UI vocabulary and the current ten consequential names; its kind union has three values. The JSON Schema at `.agents/reports/interface-contracts/schemas/interaction-intents.schema.json:22-56` is materially stale relative to those authored/live sources: its `action_name` enum (`:26-44`) omits `PROPOSE_CASE`, `EXECUTE_ITEM`, `COMPLETE_HUMAN_TASK`, `REOPEN_CASE`, and `TERMINATE_CASE`, while retaining legacy names absent from Go's accepted set. Its `case_id` and `client_cursor` patterns reject the empty proposal values. `parameters` is only a generic object (`:66-69`), whereas TypeScript declares payload interfaces and Go performs action-specific decoding. The schema therefore does not describe all observed live wire shapes.

The canonical schema conformance test repeats its own old enum (`.agents/reports/interface-contracts/tests/contract-conformance.test.ts:168-184,554-557`); that self-consistency check does not compare it to Go `AllIntentKinds`. The UI mirror test separately includes the consequential set (`src/ports/wireContract.test.ts:107-138`). These checks are distinct evidence, not proof that runtime schema validation accepts the proposal envelope. The port's base-shape comment also notes locally declared shapes beyond `types.ts` (`src/ports/contract.ts:6-9`); this inventory is limited to InteractionIntent.
