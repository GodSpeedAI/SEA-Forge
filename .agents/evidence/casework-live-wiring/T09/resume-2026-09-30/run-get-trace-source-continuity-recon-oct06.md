# `run.get` trace source continuity recon — 2026-10-06

Read-only source recon for the bounded run-observation manager. This records source facts and limits; it does not approve a manager policy or implementation.

## Reader and response shape

- `crates/sea-forge-server/src/sfwp/run_views.rs:417-436` reads a capped JSONL file into its well-formed prefix. An oversized/unreadable journal becomes empty; a malformed line stops parsing later lines. The comments explicitly describe a truncated crash tail as expected. No event-ID ordering, uniqueness, or continuity check occurs here.
- `crates/sea-forge-server/src/sfwp/run_views.rs:835-857,947-957` implements `get`: it reads `<run_dir>/trace.jsonl`, folds the rows, and copies each `TraceEvent`'s ID and safe fields into `RunRecord.trace` in input order. It does not sort, deduplicate, or establish a stable snapshot/watermark. `crates/sea-forge-server/src/sfwp/mod.rs:52-60` sets the journal cap to 64 MiB.
- `crates/sea-forge-core/src/types.rs:528-540` defines `TraceEvent.event_id` as `String`; the type specifies no global or monotonic semantics.
- `apps/godspeed-casework-go/internal/adapters/sfwp/run_trace.go:66-98,103-176` performs a live `run.get`, validates response identities/allowlisted fields and duplicate selected event IDs, retains the last 1,024 rows, and reports `TotalFrameCount` as the number of recognized rows in that response. This total and ring are observations of that read, not evidence of producer sequence or unseen events.

## Production writers and restart/recovery

- `crates/sea-forge-trace/src/lib.rs:78-91` creates a per-run recorder using `create_new(true)` and initializes its in-memory sequence to zero. `:92-122` increments that local sequence, assigns `seq_id("tev", 4, sequence)`, serializes one row, appends a newline, flushes, then syncs data. During one successful recorder lifetime, row order and IDs are sequential. IDs reset for every recorder and omit run identity; `crates/sea-forge-core/src/ids.rs:29-31,42-50` separately mints run IDs and defines `seq_id` as a formatted sequence, so `tev_0001` is not globally unique.
- The exhaustive production source matches for `trace.jsonl`, `JsonlTraceRecorder::create`, and `append_internal_error` found two recorder creation sites: `crates/sea-forge-server/src/case_dispatch.rs:732-748` and `crates/sea-forge-cli/src/pipeline.rs:279-282`. Both create a new run trace; the server appends further authority/execution/artifact/halt events at `case_dispatch.rs:795-810,920-1012` and writes settlement/authority projections separately at `:1038-1054`.
- The CLI pipeline is the only production caller of the second writer, `append_internal_error`: `crates/sea-forge-cli/src/pipeline.rs:783-791`. That helper (`crates/sea-forge-trace/src/lib.rs:22-77`) opens and validates the existing journal, refuses missing, torn, or malformed input, counts parseable rows, and appends an `InternalError` with ID `tev_(row_count+1)`. It does not validate prior IDs, run IDs, or ordering; counting rows is not equivalent to resuming the maximum prior sequence. Its tests cover a normal next ID and refuse malformed/torn tails (`:390-468`), but do not establish production crash recovery or sequence repair.
- A recorder append increments its sequence before serialization/write/flush/sync (`sea-forge-trace/src/lib.rs:98-120`). Any error can therefore leave a gap or incomplete tail; `run_views::read_jsonl` will expose only the preceding valid prefix, while the CLI helper refuses to append after a torn/malformed tail. No source path reopens a recorder and restores its in-memory sequence.
- Approval parking writes `plan.json` and `authority.json` but no run trace at `crates/sea-forge-cli/src/plan_pipeline.rs:450-464`. Resume can reuse an approved approval's run ID for the first instance (`crates/sea-forge-cli/src/commands/resume.rs:318-330`), but the production trace-writer search found no resume-specific trace recorder or `trace.jsonl` writer. Server dispatch mints a run ID and creates its trace at `case_dispatch.rs:330-354,732-748`; recovery code found in the bounded search does not reopen that recorder.
- No production run-trace deletion, truncation, rewrite, or reorder path was found in the `trace.jsonl`/recorder search. This is a bounded source search finding, not a guarantee against external filesystem mutation or unsearched generic storage operations. The append helper is explicitly append mode (`sea-forge-trace/src/lib.rs:73-76`); recorder creation is exclusive (`:79-84`).
- Case journal event IDs are a different domain: `crates/sea-forge-case-runner/src/lib.rs:31-101` and `crates/sea-forge-case-runner/src/case_ops/mod.rs:90-129` create `cev` IDs for `case-events.jsonl`. The separate SFWP event ledger also has its own cursors. Neither establishes run-trace `tev` continuity.

## Bounded conclusion

For an uninterrupted, successful single recorder, source supports append order and sequential per-run `tev` IDs. The normal production write paths append and no run-trace rewrite/removal path was found. However, source does **not** prove an unconditional immutable-prefix/unique-ID contract for every repeated `(case_id, run_id)` response: the reader tolerates valid prefixes and silently folds oversized/unreadable input to no rows; appends can fail after sequence advancement; IDs are local sequence labels that reset per recorder; the error helper derives the next ID from row count without checking existing IDs; and there is no source-provided generation, durable high-water mark, or snapshot watermark. A response's numeric safe-row total cannot identify unseen loss or establish exactly-once continuity. Manager dedupe by `(case_id, run_id, event_id)` may suppress repeat observations, but must not treat it as proof that rows are globally unique, never rewritten, or gap-free.
