## Established source facts

1. `ReadRunTrace(ctx context.Context, caseID, runID, planItemID string) (ports.RunTraceSnapshot, error)` is the port signature (`internal/ports/run_trace.go:5-8`) and SFWP method (`internal/adapters/sfwp/run_trace.go:67-177`). It invokes one `a.client.Do(ctx, NewRunGet(runID))` (`run_trace.go:72`).
2. The only current direct `run_get` sends are that method and artifact ownership lookup (`internal/adapters/sfwp/authority.go:758-765`). The latter follows `artifact_get`; this matters to global admission coverage even though it is not an initial hydration logical read.
3. Client has no callback/admission hook today. Its public call is `Do(ctx context.Context, req *Request) (*Response, error)` (`client.go:395-417`). `roundTrip(ctx, req, line) (*Response, error)` sends at line 428, retries a safe transport failure at lines 438-448, and `Do` separately retries explicit busy at lines 404-412. The busy retry repeats the roundTrip safe retry: maximum four physical calls per one logical `Do`.
4. Every actual socket write is inside `conn.call(ctx, line, timeout) ([]byte, error)` (`client.go:191-249`): request line write at 224 and LF write at 228. `Client.roundTrip` calls it once at 428 and retry call at 441. The request key is available as `req.verb` and `req.fields`/run ID; `NewRunGet` constructs `run_get` with `run_id` (`frame.go:308-313`).
5. Cleanup/join is substantive. `conn.call` defers `stopCallback`; when `context.AfterFunc` already started, it joins `callbackDone` before returning (`client.go:197-215`). `roundTrip` then discards/releases the connection after `call` returns (`:432-457`). Therefore an admission release must happen after `call`'s callback join and after roundTrip connection retirement/release, including both retry branches. A defer registered in `roundTrip` before `conn.call` would execute after `call` has returned, but before a later defer registered after it; the proposal must explicitly map this LIFO order and all early returns.
6. Production construction is not one client. `cmd/godspeed-casework/main.go:86-100` constructs a client per live capability; serve mode selects a client at later assembly, then wires its Authority at `:251-265`. Test/integration assembly also constructs clients in `internal/livetest/harness.go:247` and `internal/livestack/stack.go:61-82`. `Server` currently has no run-trace port/dependency (`internal/server/server.go:72-105`), consistent with the recon: no active production hydration caller yet.

## Budget interpretation and consequences

The approved cap is **eight logical `run.get` calls per connection cohort**, not eight physical writes: round-four approval says exactly this (`proposal-independent-approval-round4.md:9-13`), and the correction explicitly retains inspect retry while distinguishing logical calls (`contract-proposal-repair-round2.md:21-31`). The spec independently fixes selected runs 8, initial reads 8, concurrent reads 2, and minimum interval 1 second (`godspeed.casework-cognitive-environment-spec.yaml:90-95`). Counting retries as logical reads would be a material deviation. Counting only logical calls in the hydration budget while pacing every physical retry is compatible.

However, the proposal chooses exactly two process-wide slots and a one-second post-write cooldown, holds each slot through network processing and cleanup, and permits two physical sends to begin together in different slots. This is stricter in aggregate than the minimum interval and implies an eight-call cohort can take at least four one-second waves, with potentially four physical retries per logical call; retries and retry waits consume the same call context. The spec does not state a cohort wall-clock deadline or a guarantee all eight reads complete. This design can therefore time out or return availability errors for a valid cohort under normal slow/retry conditions. Proposal says expiry maps to existing typed availability, but does not state whether the manager counts a timed-out admission as one of the eight logical reads (the budget should count attempted logical `ReadRunTrace` calls, not admitted wire writes), whether later reads stop at first timeout, or how partial hydration is represented. These observable availability/partial-cohort semantics need to be stated against the approved cohort behavior before fixture release.

## Material gaps that require repair

- **Callback/API is not concrete.** The requested inventory requires exact hook signatures, but the proposal says only “admission callback”/“hook” and omits the `Config` field/type and invocation contract. Specify whether the callback acquires using `context.Context` and `*Request` (or exact run ID), returns an idempotent release function/error, and how it reports whether either write began. The distinction is required to avoid charging cooldown for cancellation before the first write while accounting for partial first/LF writes. Do not make hook absence an implicit production bypass.
- **Physical write boundary is underspecified.** “Before writing” at a call boundary is not enough: `conn.call` performs two writes (request bytes and newline), each can partially fail (`client.go:224-230`). Identify which event starts the physical-attempt cooldown, how partial write completion is timed, and whether retry admission occurs only after prior connection cleanup. The proposal asks for this proof in tests but does not define it.
- **Two-slot assignment/reuse invariant needs a complete algorithm.** It says no eligible slot plus same-run exclusion, change signal, nearest deadline, and expired idle reuse, but does not define which slot is selected, whether a busy slot with an expired cooldown remains unavailable, nor how slot replacement avoids evicting an unexpired idle run and thereby violating the per-run interval. A two-entry record bound can satisfy the global throttle but only if replacement semantics preserve every retained cooldown; exact correctness is not derivable as written.
- **Cleanup join ordering is an assertion, not an ordering prescription.** “Register admission release cleanup so it runs AFTER existing connection cleanup” is ambiguous under Go's LIFO `defer`. State exact registration/order in `roundTrip`, and ensure release waits until callback join in `conn.call`, `discard/release`, and any owned connection cancellation complete for initial and retry calls. The test list alone cannot repair an undefined production ordering.
- **Production coverage is not inventoried.** Main creates one client per live capability, and artifact provenance also performs `run_get`. Specify the one process-shared limiter's owner and how it is injected into every production client, including non-selected live-capability clients and any future client constructor used by serve wiring. `livestack` is test assembly; identify it separately. Current source has no production observation caller, so do not claim that wiring the adapter alone activates hydration or fulfills T09.
- **Cohort cap ownership must be explicit.** The limiter sees physical requests, but cannot implement the eight logical initial-read limit. Name the manager owner/API and state that admission waits/retries do not increment logical reads, while each attempted logical call does; specify what happens to remaining selected runs after one call times out. The proposal correctly says source production hydration is not yet present but the requested implementation-ready fixture semantics remain incomplete.

The specified per-run no-overlap is an additional constraint beyond the cited original cohort caps; it is not inherently unsafe, but it needs approval/justification because it changes same-run retry/concurrent-call availability. The two-slot global limit likewise introduces a throughput restriction not present in the approved logical budget.

## Required next revision

Repair the proposal with exact API signatures and event accounting, a slot reuse proof, explicit Go defer/cleanup ordering, a complete production constructor inventory, and cohort timeout/partial-result semantics. Then obtain fresh source review before fixture declarations. Until those points are resolved, no implementation is approved or released.
