## Blocking defect: expired timer while a matching run remains busy

Repair proposal algorithm steps 1 and 3 (`run-trace-physical-admission-repair-proposal-oct06.md`, “Two-record algorithm”) say a matching run must wait while busy/cooling, then describe waiting on the nearest `nextEligible` among idle records. Root adjudication closes the dangerous fallthrough by saying a matching run **must use that record** or wait; it must not use another slot. Neither record defines the wait-set when the matching record is busy and its cooldown deadline has already elapsed.

This state is reachable by the explicitly chosen lifecycle: a physical write finishes at time *t*, records eligibility *t + 1s*, then response reading or owned connection cleanup remains blocked longer than one second. The permit stays busy until response processing and connection cleanup finish (root adjudication, helper ordering; current `conn.call` can remain blocked in `readBoundedLine` at `client.go:232-249`). Once the matched busy record's timestamp is in the past, a loop that selects the nearest idle-record deadline can select this past timestamp and repeatedly create an already-expired timer. The matched record is still unavailable because `busy=true`; an unrelated eligible slot cannot be used for the same run because adjudication forbids fallthrough. With no state change, acquisition can spin and consume CPU until release or context cancellation.

Required exact wait rule: for an existing matching **busy** record, wait only for the change signal or `ctx.Done()`; do not arm any deadline from that record. For a matching idle cooldown record, wait for its future deadline plus change/context. For an absent run with no eligible slot, wait for the earliest strictly future cooldown among idle records plus change/context; ignore expired deadlines and busy-record deadlines. Explicitly retry the mutex-protected decision after every wake. This should be included in the binding proposal before declaration/fixture release.

## Disposition

The repair and adjudication close the previous callback-signature, write-event, retry coverage, production-injection, LIFO cleanup, and logical-budget gaps at proposal level. The busy-spin means the limiter's central wait contract is still not deterministic and safe under a state the proposal itself requires it to support. **No test-first fixture/declaration release is approved by this review.** A documentation-only clarification followed by a fresh independent review is sufficient; no implementation or runtime gate is authorized by this verdict.
