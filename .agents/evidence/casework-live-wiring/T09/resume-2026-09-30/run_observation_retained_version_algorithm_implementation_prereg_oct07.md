## Root-ratified architecture and private model

The root decomposition
`.agents/evidence/casework-live-wiring/T09/resume-2026-09-30/retained-publisher-private-unit-root-decomposition-oct07.md`
requires the retained publisher as a separate pure private helper before
lifecycle integration. It does not add `Next`, SSE, public contracts, or
persisted state. Root accepts a canonical image of at most `1<<20` bytes per
poller and at most 1,024 frames in the current safe window. The image contains
the exact case/run/plan identity, safe source metadata and accepted timestamp,
current source-order frames with exact event IDs/first ordinals/optional pointer
values, the complete exact-ID lifetime ledger sorted only for canonical image
encoding, and actually retained controls. Availability is one always-present
fixed-width code covering current/read/retention/terminal-retention/stop
states. Generation and highest assigned ordinal are always-present 20-digit
decimal strings. Do not add an independently mutable `nextOrdinal` copy or
speculative controls. Any further retained integration state must be added to
the full poller image before a complete-bound claim.

The existing schema/correction decisions require:

* `runObservationRetainedState` stays immutable after publication; every
  accepted candidate is built in fresh local values and never mutates its
  previous pointer, slices, pointer members, or `SeenByID` map.
* Initial accepted generation is 1. Each accepted replacement increments it
  once. Generation overflow cannot wrap; preserve the safe prior state and
  report `retainedCandidateGenerationOverflow`.
* The ledger is lifetime-wide and exact. Ordinals begin at 1 and increase in
  input source order only for exact unseen `EventID` strings. A repeated,
  rewritten, reordered, disappeared, or reappearing ID keeps its first
  ordinal. Shorter/reordered source snapshots never reset or evict IDs.
* Reject duplicate exact IDs in one source window as invalid, without choosing
  a winner. Reject a new ID when highest ordinal is `MaxUint64`; do not wrap or
  partially add IDs. Do not derive sequence/high-water from source totals or
  parse/normalize identifiers.
* Preserve source frame order. Deep-copy `ExecutionStatus` and `ExitCode` at
  ingestion; prior, source and result pointer values must not alias. `Frames`
  contains one current safe representation per frame with its first ordinal;
  `SeenByID` is the complete lifetime ledger, so the image deliberately
  contains the ordinal alongside each current frame and again in the ledger.
* Capture accepted timestamp once from `acceptedAt` only for a successful new
  generation. Rejected/invalid/overflow candidates preserve prior timestamp,
  generation, window, metadata, high-water and ledger.
* Build the entire candidate and canonical image before publication. Accept
  iff encoded length is at most exactly `1<<20`; reject one byte over and
  reject irreducible metadata without pruning retained publisher state. The
  independent initial DTO hydration pruner is not called here.
* A nonterminal over-budget candidate with prior state returns a copy of all
  prior safe fields plus only the fixed `retainedRetentionUnavailable` marker.
  Preserve the entire prior ledger so a later complete candidate can recover.
  A first over-budget candidate returns no installed state.
* A terminal over-budget candidate returns no candidate-derived value and, if
  prior state exists, returns only the exact prior safe image plus the fixed
  `retainedTerminalRetentionFailure` marker. For this unit, terminal means
  execution standing `completed`, `failed`, or `terminated`; settlement is
  never used to infer terminality. Lifecycle later owns stop-before-join and
  physical read/capacity semantics.

The candidate function will remain a pure value transform: no manager mutex,
lease/wake state, I/O, trace-port calls, auth/present-context calls, cancellation,
worker state, or lifecycle integration. The canonical marshal helper may
serialize and count bytes but will not mutate/publish state or decide the
caller-facing lifecycle action. It must use explicit ordered structs/slices,
never map iteration; sort only the ledger representation by exact opaque ID.
No whole-heap/RSS guarantee follows.

## Proposed implementation sequence after separate release

1. Add small private helpers for checked candidate validation, deep frame copy,
   exact ledger copy, one-frame safe-value copy, terminal execution
   classification, generation/ordinal overflow, and accepted-state image
   construction. Keep all helpers deterministic and side-effect-free.
2. Validate source key equality against snapshot case/run/plan; validate the
   previous-state invariants before using it; reject an invalid/duplicate
   candidate before budget or publication. Preserve the adapter's source-order
   frames and exact identity bytes.
3. Clone old ledger and window metadata into candidate-local state. Scan
   candidate frames in source order. Reuse exact prior ordinals; check ordinal
   overflow before assigning a new ordinal; add new identities only to the
   local map. Build copied frame+ordinal entries and capture new timestamp.
4. Check generation increment before commit. Starting from no state uses
   generation 1/high-water 0; prior state increments once. An overflow returns
   the explicit safe overflow outcome and no wrapped value.
5. Marshal the complete current candidate and compare encoded length with
   `runObservationRetainedImageMaxBytes`. On fit, return it as accepted. On
   nonterminal overage, discard all candidate locals and return exact prior
   state plus only the retention marker, or nil if no prior. On terminal
   overage, discard all candidate locals and return exact prior state plus
   only the terminal marker, or nil if no prior. Marker changes must preserve
   image length at the exact limit.
6. Keep `marshalRunObservationRetainedImage` as the shared canonicalizer for
   accepted candidates and assertions. Do not alter the DTO hydration helper,
   manager, ports, contract, selector, lifecycle, `Next`, or other fixtures.

## Assumptions requiring root decision before implementation

These are implementation gaps not completely fixed by the current helper
fixture or retained-publisher decomposition. Recommended defaults are stated
for efficient review; do not silently encode them:

1. **Availability after ordinal/generation overflow.** The tests require a
   nonwrapping outcome and safe prior state but normalize expected availability
   from the result itself. Recommend a copied prior with only
   `retainedRetentionUnavailable`; do not accept the old value as the requested
   current observation after a refused candidate. Generation exhaustion can
   never recover; root must decide whether it additionally maps to
   `retainedStopScheduling` or remains a retention-unavailable state for later
   lifecycle handling. Ordinal exhaustion may recover for later candidates
   containing only already-seen IDs, so it should not be terminal.
2. **Prior-state invariant validation.** Recommend reject as invalid if key is
   inconsistent, generation is zero, a ledger ordinal is zero or duplicated,
   ledger maximum disagrees with `HighestOrdinal`, a current frame's ID/ordinal
   does not exactly match the lifetime ledger, duplicate IDs exist in the
   window, current frame count exceeds 1,024, or total count is negative / less
   than retained length. Confirm whether malformed prior state returns
   `retainedCandidateInvalid` with nil state (recommended) or a safe copy of
   the prior state.
3. **Adapter validation boundary.** `RunTracePort`'s SFWP implementation already
   validates standing enums, frame-kind/status metadata, timestamps, nonblank
   exact IDs, uniqueness, response identity, and the 1,024 projection. The
   helper fixtures independently require duplicate-window rejection and
   bound checks. Recommend helper also checks key identity, nonblank/UTF-8 IDs,
   frame bound/count consistency, duplicate IDs, and the current contract enum
   allowlists defensively; confirm whether to trust the existing port contract
   for enum/timestamp checks instead of repeating it.
4. **Timestamp normalization.** Tests use UTC and require exact
   `acceptedAt.Format(time.RFC3339Nano)`. Recommend preserve this exact format
   including its supplied offset (do not normalize an instant silently); confirm
   no UTC conversion is intended.
5. **Rejected first terminal candidate.** Without prior state, the helper has
   no old values on which to install a terminal marker. Recommend return typed
   rejection and nil state; the lifecycle already owns the returned snapshot
   and can stop after actual read return. Confirm no auxiliary candidate
   terminal bit should be added to `retainedCandidateResult`.
6. **Read-unavailable state input.** The helper receives only a snapshot, not a
   read error. Recommend a valid later full candidate may recover a state marked
   `retainedReadUnavailable` or `retainedRetentionUnavailable`, resetting only
   availability to current on successful acceptance. A previous terminal
   failure or stop-scheduling state should reject further candidate publication.
   Confirm expected outcome/state for these two blocked input states.
7. **Canonical UTF-8 and identity bytes.** Go JSON marshaling replaces invalid
   UTF-8 in strings. The SFWP decoder ordinarily supplies valid strings, but
   custom port implementations can violate that assumption. Recommend reject
   invalid UTF-8 identity/frame strings to prevent distinct opaque IDs from
   collapsing in canonical JSON. Confirm whether this defensive validation is
   required.
8. **Canonical frame/count values.** The port `TotalFrameCount` is the source's
   recognized response count before the 1,024-frame adapter projection. It may
   be greater than the retained frames and is not a continuity count. Recommend
   retain it exactly and derive `omitted = TotalFrameCount - len(Frames)` only
   after requiring nonnegative total and total >= retained frame length; do not
   enforce monotonic totals between generations. Confirm that neither source
   count nor truncation is inferred from the ledger.

Until root answers the questions above, this file is a preregistration and
recommended design only. It does not release implementation; no user approval
is requested. Root owns the architecture choices.
