## Design assessment

The proposed representation is suitable in principle for the separately scoped pure helper. The root decision fixes one immutable state with exact poller key, accepted version metadata, current ordered window, complete exact-ID lifetime ledger, high-water/generation counters, and a bounded availability marker. The helper has no manager, lease, I/O, authorization, or `Next` surface (`run_observation_retained_version.go:31-80`). This stays within the root decomposition's helper-before-lifecycle boundary (decomposition lines 3-14, 26-36).

The canonicalizer uses an explicit struct, source-order frame slice, and sorted ledger projection (`run_observation_retained_version.go:83-117,124-171`). It serializes one exact image with a schema marker, key, source metadata/counts, frame values and per-frame ordinals, full ledger, high-water, generation, and availability. The ledger's event IDs and ordinals also appear in current frame entries by design; that is necessary to represent both current window and lifetime history, and is explicitly ratified in the preregistration/root decomposition. `sort.Strings` is used only to canonicalize ledger serialization, not to change source order or opaque IDs. No extra mutable next-ordinal value is stored.

`fixedUint64Decimal` yields a 20-byte decimal representation for uint64 values, including `MaxUint64`; the availability enum occupies one decimal digit and is guarded against out-of-range values (`run_observation_retained_version.go:19-29,119-129`). The image budget constant is exactly `1<<20`, and the window cap is 1,024 (`:14-17`). Optional frame fields are copied to serialization-owned values and preserved as pointers only when present (`:131-145`). The focused tests cover `MaxUint64` fields and every availability code at constant encoded length (`run_observation_retained_version_test.go:367-408`), plus measured exact-limit acceptance and metadata-only +1-byte refusal (`:410-457`). This is a serialized-image bound only; it makes no heap, transient-candidate, or process RSS guarantee, consistent with root decision line 11.

Atomic candidate construction should use a fresh ledger, frame slice and optional pointer values; never mutate the prior image. The fixtures verify source/prior/result optional pointer nonaliasing (`run_observation_retained_version_test.go:91-141`), exact ID ordinal preservation across reorder, shorter window, disappearance/reappearance and source ordering (`:143-218`), and deep prior-state/image equality for candidate refusal (`:242-306`). Duplicate IDs in one source window are rejected without selecting a winner (`:220-240`). The 1,024/1,025 source-window boundary is covered (`:460-476`). These expectations align with root decision lines 5-11 and the assignment lines 92-126.

The actual SFWP adapter supports the bounded helper's trusted-input precondition. `ReadRunTrace` validates nonblank requested key, source response identity, execution/settlement vocabularies and present trace record before returning a snapshot (`internal/adapters/sfwp/run_trace.go:67-97`). It allows only known frame kinds, nonblank event IDs, RFC3339 timestamps, unique IDs, and valid command metadata; it keeps at most 1,024 source-order tail frames while preserving total count (`:99-176,254-292`). The `RunTraceSnapshot` contract defines total as recognized frames before port retention and explicitly says it is not source-journal completeness (`internal/ports/run_trace.go:10-20`). Contract vocabularies include terminal execution values `completed`, `failed`, `terminated`; settlement values are separate (`internal/contract/contract.go:426-438`). Thus it is reasonable for this private helper not to duplicate every adapter validation, while still checking requested key identity, `TotalFrameCount >= len(Frames) >= 0`, <=1,024 frames, and duplicate IDs. Root decision lines 6-7 explicitly adopts that boundary and disclaims arbitrary custom-port sanitization.

The helper state has `ObservationState`, although a successful `RunTraceSnapshot` has no such field (`run_observation_retained_version.go:38-49`; `internal/ports/run_trace.go:13-21`). The fixture's accepted state uses `validated` (`run_observation_retained_version_test.go:38-44`), which is the correct successful-read interpretation. The implementation should set it as that fixed derived value; it should not claim it came from the port. Read errors remain a distinct lifecycle/control path, not an accepted snapshot. This is a documentation clarity point, not a blocker.

## Release-blocking evidence gaps

The design choices themselves are resolved by root; the current fixture does not assert several of those exact choices. Because the code is still a stub, these assertions are the only source contract that can prevent a later implementation from satisfying tests while choosing the wrong marker or terminal rule.

1. **Overflow outcomes do not pin the exact required availability.** The ordinal-overflow test accepts `result.State.Availability` as its own expected value (`run_observation_retained_version_test.go:497-501`), and the generation-overflow test does the same (`:527-531`). Root requires ordinal overflow to return `retainedRetentionUnavailable` (or `retainedTerminalRetentionFailure` for a terminal candidate), and generation overflow to return `retainedStopScheduling` (`retained-publisher-algorithm-root-decisions-oct07.md:5`). The current comparisons only prove that the chosen marker was the sole state change; they allow the wrong marker. Add exact marker assertions for nonterminal ordinal overflow and generation overflow. If terminal ordinal overflow is in the fixed behavior contract, add that case and require terminal-retention-failure.

2. **Terminal classification is not discriminated from settlement.** The terminal over-budget fixture uses execution `failed` and settlement `rejected` together (`run_observation_retained_version_test.go:323-329`). A faulty implementation that infers terminality from settlement would pass this test. Root explicitly says settlement never determines terminality (root decisions line 9) and defines terminality as execution `completed`, `failed`, or `terminated`. Add a valid nonterminal execution candidate with a terminal-looking settlement and prove it takes the nonterminal retention marker, or add a terminal execution with `unsettled` settlement to prove the other direction.

3. **Root's terminal marker state cannot be proven final.** Root requires that a prior `retainedTerminalRetentionFailure` or `retainedStopScheduling` state reject later candidates and preserve its marker (`root decisions line 10`). The current terminal test checks only the first over-budget terminal refusal; it never submits a later candidate against that marker. Add a focused assertion that subsequent candidate construction does not accept/update it. This need not test worker joins or lifecycle scheduling, which are out of this helper's scope.

4. **Source total versus retained-window semantics lack a positive discriminating fixture.** The port explicitly permits `TotalFrameCount > len(Frames)` when it retained only the last 1,024 frames (`internal/ports/run_trace.go:10-20`, adapter `:157-175`); the helper decision says preserve that value and do not infer monotonic totals (`root decisions line 7`). Current helpers set total equal to frame count (`run_observation_retained_version_test.go:29-35`), except the terminal oversize fixture sets total 2 for one frame (`:323-326`) but then focuses on marker-only refusal and never asserts the accepted image's count/truncation metadata. Add a fitting accepted snapshot with total greater than the current window and assert the total is preserved and omitted/truncated fields reflect only `total - len(window)`. This keeps source count distinct from lifetime ledger size.

These are focused source assertions, not reasons to broaden the helper into adapter validation or lifecycle behavior. The existing terminal values are valid (`failed`, `rejected`, `timed_out`); the previous invalid-value defect was corrected and the frozen fixture review correctly approved it only for a focused semantic RED attempt. The current tests still do not establish an actual RED. The independent current-candidate RED must be run and reviewed separately as required by root decomposition lines 9-14 and root decision line 3.

## Minimal next step and boundaries

Keep the architecture as preregistered. Before releasing algorithm implementation, add the four narrow assertions above to a new immutable fixture candidate, obtain source re-review, then independently run and accept RED for the exact frozen test candidate hash. The implementation should follow root decisions exactly: first generation 1; accepted replacements increment once; generation overflow preserves a deep safe copy with stop-scheduling; ordinal overflow preserves it with retention-unavailable or terminal-retention-failure as applicable; exact opaque IDs retain first ordinals over all accepted windows; rejected candidates do not change timestamp, generation, metadata, window, high-water, or ledger; a fitting recovery after nonterminal refusal can reuse old IDs and add new ones. Terminal classification is execution-only. No pruning, ID normalization, source-total inference, or candidate-data retention on refusal.

The trusted SFWP adapter precondition is supported for production adapter outputs, but `RunTracePort` is an interface and custom implementations can violate it. The helper's root decision consciously excludes custom-port sanitization and requires its explicit local bounds/identity/duplicate checks. Keep that qualification in any implementation claim. A future manager/poller image may carry additional retained controls outside this helper image; count those in the integrated per-poller bound before claiming the full manager state is <=1 MiB (decomposition lines 16-24; root decision line 11). This review approves neither lifecycle integration, scheduling, lease ownership, cancellation, joins, manager capacity, `Next`, SSE, contracts, nor persistence.
