# T09 contract extension proposal

**Status:** Operator approved; independent proposal architecture approved in round four. This remains a design proposal only: no source, contract, or normative spec changes are included, and the proposed limits are not implemented policy.

## Recommendation

Proceed with the operator-approved scoped T01 contract amendment before T09 implementation. Keep the existing SFWP `run.get` and Ask operation. The catalog advertises that operation as `thoth.ask`; the actual tagged kernel request is `{"verb":"ask"}` (`Request::Ask`). The gateway must send that exact wire tag; `thoth.ask` is not a JSON verb alias. Add a typed `execution_observation` SSE event and authenticated Go ask endpoint returning the complete existing `ThothAnswerView`. Do not add a Rust request variant or dependency.

Resource-bound prerequisite: source inspection found that the Go SFWP client has no response-line byte cap today (`client.go` calls `bufio.Reader.ReadBytes('\n')`). The operator approved proposing an additive client guard before T09 consumes large `run.list`/`run.get` responses: a 32 MiB default maximum response line, with a documented lower per-client override only if desired. An over-limit line must be detected incrementally, close the connection, and return typed `unavailable` before JSON decoding. This changes resource behavior for all SFWP responses. The cap is approved in this proposal but is not implemented; until then, call counts do not bound response allocation. No Rust protocol or dependency change is proposed.

The canonical D-1 UI–gateway contract is `.agents/reports/interface-contracts/typescript/types.ts`. It already defines `CognitiveObjectKind = 'execution_trace'` and `CognitiveObject.parent_id`; the UI maps `execution_trace` to its internal `run` kind in `apps/godspeed-cognitive-ui/src/model/derive.ts`. T09 needs Go to emit child objects for real runs, not a new object kind. The canonical contract already has a different `ExecutionObservation` type for invocation outcomes; name the new trace DTO `RunTraceObservation` and its frame DTO `RunTraceFrame`.

## Current implementation gaps

Go `projection.LiveSource` fetches `run.list` summaries, but `projection.Build` emits only stage and work-item objects. The Go SFWP adapter calls `run.get` only to prove artifact ownership and retains only fields needed for that check. The SFWP `RunRecord` already exposes trace and evidence rows.

The live SSE handler emits snapshots from case-event revisions. The SFWP event bus does not publish per-run command trace rows, so the existing `execution_progress` payload cannot be populated from live kernel events. That payload also requires numeric `progress_percent`; the kernel provides no numeric progress measurement. Keep `execution_progress` for sources that actually report percentages and never infer one from command starts, exits, or settlement.

Current resource facts: `run.list` walks all run directories and has no pagination; its optional `case_id` filters returned/readable records after global directory enumeration. Go currently calls the unscoped `NewRunList()`, although the existing Rust request already accepts `case_id`. Rust caps each JSONL journal at 64 MiB and individual JSON record at 4 MiB, not the aggregate `run.get` response. `run.get` may read multiple separately capped journals and records. Once implemented, the proposed 32 MiB Go response-line cap will bound each individual response line in the client, but it will not cap upstream filesystem scan/read/serialization work or cumulative bytes across a hydration cohort and retries; do not claim otherwise.

Go has no Thoth ask port or HTTP route. The kernel catalog advertises `thoth.ask`, but the actual request enum uses JSON tag `verb: "ask"`. `Request::Ask` is protected, takes `kind`, `subject`, optional `purpose`, and optional `case`; the handler uses the verified effective actor as asker. The current UI `NarrationBeat` has text, citations, and optional directives but no complete Thoth disclosure envelope.

## Proposed execution observation

The Go projection should emit one `execution_trace` child per case-owned run, preserving the kernel-provided `run_id` and `plan_item_id` parent relationship. The child carries standing; live trace observations are a separate side channel keyed by `run_id`. Do not add frames to, rewrite, or mutate captured historical snapshots. Rehydrating current run observations after reconnect must not alter facts retained for an older world cursor. While viewing history, show that cursor's captured run standing and do not overlay current live observations.

The new side-channel payload is distinct from the canonical `ExecutionObservation` interface, which describes invocation outcomes. Define `RunTraceFrame` with actual `TraceRow.event_id`, snake-case `kind`, and `timestamp`; include `execution_status` and `exit_code` only when those values exist on the actual `command_finished` row. `RunTraceObservation` contains `run_id`, `observed_at`, `frames`, `observation_state`, `total_frame_count`, `retained_frame_count`, `omitted_frame_count`, and `truncated`. Frame identity is the pair `(run_id, event_id)`; never synthesize event identity from a case cursor.

Allow only these safe trace kinds: `run_started`, `item_activated`, `command_started`, `command_finished`, `item_completed`, `item_failed`, `item_terminated`, `human_task_completed`, `run_halted`, and `run_finished`. Do not forward raw trace payloads, command arguments, environment, stdout/stderr, actor IDs, or artifact content. Evidence remains navigable through the existing authenticated artifact route.

Add `execution_observation` to canonical `StreamEventType` and define a named `RunTraceObservationEvent extends StreamEvent<RunTraceObservation>` arm whose `event_type` is the literal `execution_observation`. `RunTraceObservation` is a bounded cohort envelope: `case_id`, `observed_at`, `run_list_state`, `observation_state`, optional listed/selected/validated/unreadable/unavailable/omitted run counts, `hydration_read_budget` (`limit`, `reads_attempted`, `exhausted`), and at most eight runs. Counts are present only after a complete `run.list`; if it fails or exceeds the client cap, counts are absent and state is `unavailable`, never zero/complete. `omitted_run_count` means listed case-owned summaries not attached because the eight-run cohort or shared-poller capacity was exhausted; unreadable and failed/mismatched `run.get` candidates have separate counts. `observation_state` is one of `complete`, `no_runs`, `capacity_limited`, or `unavailable`. `hydration_read_budget.exhausted` is true only when the eight-read limit prevented a known candidate from being validated. Each nested run observation carries the real `run_id`, `plan_item_id`, execution and settlement standing, bounded frames, and accurate total/retained/omitted/truncated metadata.

The current generic `StreamEvent<T>` is not a discriminated union; the parser must narrow to this named arm after validating event type, cursor, timestamp, and payload. In `src/adapters/http/httpCaseworkAdapter.ts`, add it to the native `EventSource` listener allowlist; fetch streaming uses the same parser. Route observations before the ordinary case-cursor check. For this event only, do not compare `event.cursor` with `lastCursor` and do not update `lastCursor`. Ordinary snapshot/revision events keep their existing monotonic case-cursor behavior.

An observation envelope cursor is informational and copied from the latest real case cursor known to the gateway. Never create a logical case cursor for a trace row. Write the SSE frame without an `id:` field, so `Last-Event-ID`/`?last=` remains the case-revision resume cursor. Each new SSE connection starts a hydration cohort: issue one `run.list` scoped with the existing optional `case_id`; after a successful complete result, order active runs first, then other nonterminal (`pending`, `enabled`) runs, then terminal runs (`completed`, `failed`, `terminated`) by newest finished/started time and run ID. Consider at most the first eight candidate summaries and perform at most eight initial `run.get` reads for that cohort. Validate each result's exact `run_id` and `case_id` against the requested case before projecting it. No automatic fanout occurs for omitted candidates; a later new connection cohort may try again. Reuse an existing shared poller's bounded current buffer when one is already running; all hydration/poll reads still obey the shared two-read concurrency limit.

The UI identity cache belongs to the `subscribeEvents` subscription and persists across its internal native/fetch reconnects, but is cleared on case switch/dispose. Bound it to at most 32 run keys, 4,096 `(run_id,event_id)` identities total, and 1,024 identities per run. Use LRU eviction for terminal run keys and evict the oldest identities when either ID cap is reached. Never evict an active run key solely to admit another active run: if all 32 keys are active, drop the unseen run's observation frames and report a typed adapter-local capacity notice while leaving case revisions flowing. Rehydration replaces the current bounded observation annotation by run/event IDs; it does not append duplicate UI log entries. The guarantee is bounded dedupe only while an identity remains cached; after eviction, replay may be delivered again. Do not promise unbounded exactly-once delivery. A capacity notice directs the user to resubscribe or switch away and back to start a fresh bounded cache; it does not fabricate trace claims.

The operator-approved proposal sets these cohort and poll limits; they remain unimplemented and are not current settings: at most eight selected runs and eight initial logical `run.get` calls per hydration cohort, plus a separate `run.list` call for selection; at most 16 active shared `(case_id, run_id)` pollers per gateway process; at most two concurrent `run.get` reads; and no poll faster than once per second per run. Each logical inspect call retains the client's existing one fresh-connection retry after a transport failure. Retain at most 1,024 safe metadata frames per run. Cap the serialized initial hydration envelope at 1 MiB across all selected runs; when it would exceed that cap, omit oldest frames deterministically and report exact omitted counts. Later poll updates contain only newly observed frame IDs; their per-frame metadata is allowlisted and the bounded poller ring limits retained memory. The 1 MiB cap applies only to projected initial hydration metadata; it does not bound cumulative transport bytes across `run.list`, `run.get` calls, retries, or an indefinitely open SSE connection.

For a successful complete `run.list`, report exact listed/selected/validated/unreadable/unavailable/omitted counts. If more than eight eligible case runs exist, or the shared 16-poller capacity prevents attaching all selected runs, report `capacity_limited` and the known omitted count. If the eight initial read budget is exhausted while additional known candidates remain, set `hydration_read_budget.exhausted`; do not launch more reads. If a run is denied, unavailable, malformed, or `run.get` returns an owner mismatch, count it unavailable and project no frames for it. If `run.list` itself is refused or its response exceeds the proposed client cap, report typed `unavailable` with counts absent, never a complete empty run set. Since `run.list` has no pagination and enumerates all run directories internally, even a successful case filter does not bound upstream enumeration work.

Each `run.list` or `run.get` response line has a proposed 32 MiB maximum, enforced incrementally by the Go client before decode; concurrent `run.get` reads are capped at two. The hydration work bound is one `run.list` selection plus at most eight logical `run.get` calls per connection cohort. This is not a total-wire-byte bound: `run.list` is separate from the eight `run.get` calls, inspect calls retain their existing single fresh-connection transport retry, and later SSE poll/maintenance frames can continue for the life of a connection. The 32 MiB limit applies per response line and the 1 MiB limit applies to the projected initial hydration envelope; neither limits aggregate kernel file reads, run-list enumeration, or cumulative transport bytes. Rust may read several independently capped journals and records to construct each response. The 64 MiB per-journal ceiling is not an aggregate `run.get` response bound. Do not multiply the per-line limit into a cohort-wide or total-wire claim. The cap is approved as a proposal but remains unimplemented; T09 must not claim current bounded response allocation before implementation.

Stop a poller when its run is terminal (`completed`, `failed`, or `terminated`) or has no subscribers; cancel and drain any pending read before removal. No more than 16 pollers may exist process-wide. If capacity is full, omit new pollers and expose `capacity_limited`; do not evict an active run just to fan out to a new connection. These limits do not change execution authority or settlement standing; a command exit never implies settlement.

## Proposed Thoth ask contract

Add authenticated `POST /api/ask`. Its `kind` is restricted to exactly the kernel's nine `QuestionKind` wire strings: `ask_capability`, `ask_operation_requirements`, `ask_authority_requirements`, `ask_projection_support`, `ask_environment_status`, `ask_failure_explanation`, `ask_evidence_for_claim`, `ask_available_affordances`, and `ask_why_denied`.

The HTTP JSON shape is `{ "kind": "...", "subject": "...", "purpose": "...", "case": "..." }`; `purpose` and `case` may be omitted, matching existing kernel defaults/optionality. The body carries no actor or role, and strict decoding rejects unknown fields. Reject an empty whitespace-trimmed subject, a supplied empty `case`, unknown kind, malformed JSON, and oversized bodies before contacting the kernel. The kernel uses Rust `str::len()` and rejects more than 500 UTF-8 bytes for `purpose`, despite the source comment saying “chars.” Count UTF-8 bytes, not JavaScript UTF-16 code units or Unicode scalar values. The kernel does not require nonempty purpose; omitted purpose defaults to `planning`.

The existing SFWP request is `{"verb":"ask","kind":...,"subject":...,"purpose":...,"case":...}`. `Request::Ask.actor_id` accepts the field alias `asker`, but there is no alias for `verb`. The handler uses the identity gate's verified effective actor, ignoring a caller-nominated `actor_id`. The gateway builds its protected request with service identity in `actor: {actor_id, role}` and authenticated session identity in `on_behalf_of`; it sets request `actor_id` to that effective session actor. The catalog string `thoth.ask` is a discovery label, not the request tag. The kernel applies disclosure policy and writes ask/answer records; the gateway never decides which claims may be disclosed.

`service::ask` durably commits question and disclosure records, so this POST needs its own limiter. Add an Ask-specific per-session and per-IP limiter before its handler; do not assume existing POST protections apply to every route, and do not change `rateLimitIntent` or its accounting. The approved proposal recommends defaults of 6 asks/minute per session with burst 2, and 20 asks/minute per IP with burst 4. These values are not implemented policy. Use the same session identity and remote-IP keying conventions as the intent limiter, but separate Ask buckets. Apply `requireSession`, `requireCSRF`, then the Ask limiter.

The approved proposal recommends an 8 KiB body limit for this route; it is not implemented policy. Implement it with an Ask-specific strict decoder that rejects excess bytes, unknown fields, trailing JSON values, and malformed or wrong-shaped JSON before the SFWP call. The shared `decodeStrict` currently caps bodies at 1 MiB; that general bound does not satisfy this proposal's smaller Ask limit.

Return the complete SFWP `ThothAnswerView`. The Rust view stores several enum spellings as strings, so type the contract unions to these exact wire values:

- `ThothDisposition`: `answered | partial | denied`.
- `ThothFreshness`: `current | stale`.
- `ThothClaimClass`: `identity | architecture | declared_capability | installed_capability | demonstrated_capability | authority_requirements | environment_status | failure_condition | security_implementation | customer_private | credential_bearing | policy_thresholds`.
- `ThothClaimStatus`: `unknown | unsupported | declared | installed | available | validated | demonstrated`.

Preserve every answer field: `answer_id`, `question_id`, `disposition`, `claims`, `omitted_claim_classes`, `snapshot_ref`, `freshness`, `assurance`, `limitations`, `authority_notice`, and `answered_at`. Each claim preserves `claim_id`, `claim_class`, `subject`, `status`, `statement`, `snapshot_ref`, `evidence_refs`, `settlement_refs`, and optional `capability_record_ref`.

Keep governed `denied` and `partial` answers as successful response bodies; transport and identity refusals remain typed errors. Extend the UI narration result with optional grounded answer metadata; render disposition, freshness, assurance, limitations, omitted classes, authority notice, and exact references. Derive `thoughtText` only from returned template-generated claim statements; for empty/denied answers, use fixed UI copy stating disposition. Map citations only from returned evidence, settlement, and capability-record references. Do not create claims, citations, or directives. Thoth accepts finite kind/subject queries rather than arbitrary free text, so unsupported questions get an honest unsupported response; the adapter must not claim general conversational answering.

## Alternatives and risks

1. **Proceed with the approved additive contract and response cap (recommended).** T09 can show actual run objects, bounded observed command frames, and grounded Thoth answers. Changes are optional/additive for existing consumers, but require normative spec and golden updates. The approved 32 MiB client response-line cap changes resource behavior for all Go SFWP reads and must be implemented before bounded response allocation is claimed. The cohort/poller/UI limits and Ask-rate settings are approved proposal values, not current runtime policy.
2. **Keep the current wire contract.** Emit existing run children and snapshots only, keep live narration unavailable, and do not claim live command-frame progress. This avoids a public contract amendment but does not satisfy T09's planned real-SSE execution frames or grounded live narration; T09 must be replanned and cannot claim those seams complete.
3. **Use only the existing `execution_progress` event.** This works only if a source supplies truthful numeric progress and declared phase. The kernel run trace supplies neither, so this option cannot represent planned kernel execution without false progress.
