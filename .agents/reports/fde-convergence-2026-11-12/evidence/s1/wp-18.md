## Design decisions and deviations

1. Promotion and re-pin are carried by the existing transition: a promotion is `decide` on a `world_transition` request with an `approval_id`, so there is one approval path. The approval is bound to the proposal by the proposer's escalation request carrying `claims.proposal_digest` (claims are recorded with the decision and are never a verdict input). `promote` checks the recorded claim against the proposal it is given (`DECISION_DIGEST_MISMATCH`), and the transition's `resource_id` against the candidate. A re-pin binds `claims.repin_digest` = sha256(JCS({from, to, reason, of_pin})) (`repin_digest`).
2. The pin is a `world_pin` record in the same CEP ledger (`world-pin:<operation_id>`), not a new store; the current pin is the last `to_world_ref`, else the baseline = the first configured world. There is deliberately no unguarded "initial pin" verb. The candidate world is registered by host configuration (the registry is built from it); a transition to an unregistered world is refused (`TRANSITION_REFUSED`). The E section 7 saga "register candidate, approve, pin, record" is therefore: configuration registers, then approve, decide, pin. A crash after the transition and before the pin is finished from the recorded transition, never decided twice (`a_crash_between_the_transition_and_the_pin_...`). There is no reconciler job; a retried promote completes it.
3. Regression refusal code. The brief says a failing or absent matrix is `REGRESSION_FAILED`; G NT-21 says lost capability and unlisted weakening each refuse promotion (with `LOST_CAPABILITY` and `UNLISTED_WEAKENING`, marked as codes to be defined). The matrix carries `refusal_code` = `REGRESSION_FAILED` when any row has it, else the first other row code, and SEA-Forge refuses with that code; an absent or inconsistent matrix is `REGRESSION_FAILED`. NT-08 therefore yields `REGRESSION_FAILED` exactly.
4. A matrix that lists a weakening (`escalated: true`) is refused `ESCALATED_APPROVAL_REQUIRED`: the "escalated approval class" does not exist in the CEP approval path (one human approval floor) and creating one would be a second authority path. Fail closed until WP-22 / A3.
5. Matrix pairing of elements is by comparison expectation id; `intended_changes[].supersedes` is the explicit old-to-new mapping E asks for (needed so an undeclared element becomes the declared one). "Coverage unchanged" is defined as the same comparison profile digest and silent evidence sources in the old and candidate comparisons.
6. Re-classification (`derive --events-world`, `compare --reference-world`) is new in RealityTrace code outside the WP-18 list, needed for AT-13 ("the same records under the old and new world"): derive filtered events by `world_ref == classifying world`, so the same ledger rows could not be classified under two worlds. It is opt-in; without the flags the behaviour and the input-set hash are unchanged. The `observed-representation.v1` contract is closed, so the events' world is recorded only inside the input-set hash.
7. The held-out rule excludes episodes by episode key (the frozen rule of `episodes.yaml`); the rule document and the capability-delta definition are pinned by a digest supplied from outside (`--rule-sha256`, `--frozen-sha256`), standing in for the pre-registration, which has no field for them (the frozen files were not touched).
8. SEA-Forge does not recompute the matrix: it checks the matrix is the proposal's, its id is its digest, the verdict agrees with the rows, and refuses on any failing row. Recomputing the transitions would duplicate the table. The RealityTrace and SEA-Forge JCS agree on a RealityTrace proposal fixture (`at12_the_digest_of_a_realitytrace_proposal_...`, copy of `contracts/fixtures/revision-proposal/valid/with-supersedes.json`).
9. `PROPOSER_IS_APPROVER` and the requester checks in `world_pin.rs` are defense in depth: the same rule is enforced by the policy engine (`requester != actor` in `matches_approval_resolution_parameters`) and by `resolve_approval`; the first two layers cannot be disabled by policy alone (mutation above).
10. Freezing a new episode is not refused when its world is not the pinned one: `case.record.append` has a closed error enum and no contract code for it. The AT-13 test only shows that a new episode freezes against the new `world_ref` and the old records keep theirs.

## Review fixes (independent adversarial review of ee93ee87..69357a5d)

Tests in `crates/sea-forge-authority/tests/world_pin.rs` (`f3_*`, `f4_*`, `f8_*`, `f10_*`, `the_approver_may_not_be_the_proposer_...`) and `crates/sea-forge-server/tests/conformance_world_pin.rs`. Each guard was removed once and the new test seen failing, except as noted.

- F3 matrix: an empty matrix is refused (it is also caught by the coverage rule, so removing the empty check alone changes no test). The approver's decision is now bound to the matrix: the escalation carries `matrix_id` and `held_out_rule_sha256` claims next to `proposal_digest`, and promote compares both with the decision and the request (`DECISION_DIGEST_MISMATCH`), so a different self-consistent matrix swapped in after approval is refused. A passing matrix must cover the proposal: every `intended_changes` element is the `new_expectation` (or `old_expectation`) of a row, every `supersedes` id an `old_expectation`, every diagnosis and held-out episode an `episode_ref`. The server validates the matrix against RealityTrace's `regression-matrix.v1` (vendored by digest in `crates/sea-forge-server/contracts/rt/`, `DIGESTS`, equals `fde-sxr-integration/contracts/regression-matrix.v1.json` when that worktree exists) and refuses `MATRIX_INVALID`. RESIDUAL TRUST: SEA-Forge still cannot recompute the transitions without RealityTrace. The rows' classes and results are the proposer-supplied matrix's word; the approver's bound `matrix_id` covers which matrix, not that it is true. Coverage cannot tell whether a row's element exists in either world, and extra compared episodes are allowed (RealityTrace compares a superset).
- F4 atomicity: promote and re-pin run under one per-root lock; `commit_pin` re-checks that the pin it moves from is current and takes a per-position ledger key (`world-pin-slot:<n>`), so a committer in another process also loses with `PIN_STALE`. Test: `f4_two_concurrent_promotions_...` (6 rounds, exactly one commits, the loser is `PIN_STALE` and spends no transition). Removing the lock alone fails the test; the cross-process slot key has no test of its own.
- F8: a promote replay after a re-pin returns `PIN_SUPERSEDED` (a code in `world_pin.rs`, not a closed contract) and pins nothing. The baseline is `cep_authority.pinned_baseline` (a configured world name) or the single configured world; with several worlds and none named, `authority_promote` and `authority_repin` refuse `cep_pin_baseline_ambiguous` and `authority_pin` reports `current: null`. OPEN ITEM, not done: the freeze path (`episode.frozen`) does not refuse a `world_ref` that is not the pinned world, because `case-record-append.v1` has no usable code (the enum is SCHEMA_INVALID, KIND_UNKNOWN, IDEMPOTENCY_CONFLICT, EPISODE_REF_DIGEST_MISMATCH, RESULT_INVALID, FREEZE_KEY_EXISTS, FREEZE_MISSING, FREEZE_INCOMPLETE, SELF_SETTLEMENT_REFUSED, EXPLORATORY_NOT_SETTLEABLE). - F10: `world_pin_attempt` records cap their fields (message 512, target 256, actor 128 characters) and a caller keeps at most 50 per hour; the 50th is an `ATTEMPTS_RATE_LIMITED` marker and later ones in the window are refused without a record.
