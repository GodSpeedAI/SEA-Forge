## Verdicts

The spike asserts what the library does today. PASS means "obtainable through the public API"; FAIL means "not obtainable".

| Case | Truth value per policy (public API) | Bound instances |
|---|---|---|
| a. empty facts | PASS | n/a |
| b. one satisfying, one violating | PASS (policy-level only) | FAIL |
| c. unknown (missing attribute) | PASS | FAIL |
| d. operation-bound policy | PASS via the separate application evaluator | FAIL (no instances; context holds input fields only) |

- a: `case_a_empty_fact_set`. Both universal policies return `Some(true)` over zero instances (vacuous truth), with 0 violations. `validate()` reports evaluated=2, errors=0.
- b: `case_b_satisfying_and_violating` returns `Some(true)` for an executed Step with an Approval and `Some(false)` for an executed Step with none. `case_b2_mixed_instances_report_one_policy_level_result_only` has one satisfied and one violating Step. It yields a single `Some(false)` and exactly 1 violation. The violation message is "Policy 'executed_steps_have_approval' was violated" and `Violation.context` is `{}`. The result does not say which Step failed.
- c: `case_c_unknown_from_missing_attribute`. An Evidence instance with no `retention_days` gives `is_satisfied_tristate == None`. The bool `is_satisfied` collapses to `false`. One violation is emitted, with the same severity as a real violation and the message "evaluation is UNKNOWN (NULL)". Adding a second Evidence with `retention_days: 5` gives `Some(false)`, because False dominates Null under forall.
- d: `case_d_operation_bound_policy`.
  - `Graph::is_operation_bound_policy` is public and returns true. `validate()` skips the policy (total_policies == 2).
  - `Policy::evaluate` against the bare graph returns `None`. This is the known L9 limitation: terms do not resolve.
  - The public `application::evaluate_precondition(&Expression, &ApplicationPolicyContext) -> True|False|Unknown|Error` evaluates it correctly in a typed context:
    - input `case_status=open` gives True.
    - input `closed` gives False.
    - input missing gives Unknown.
  - The bound policy's expression comes from `Policy::expression()`. The binding comes from `ApplicationContract.operations[i].access = PolicyGoverned{bindings:[{policy, enforcement_point, failure_code}]}`.
- Extra: `facts_as_sea_source_round_trip` shows `instance x of "Step" {...}` text appended to the model parses and evaluates (`Some(false)`).

## How facts are represented today

- An instance is `(namespace, entity type, name)` plus a `HashMap<String, Value>` of fields. Its id is `ConceptId::from_concept(ns, "Type:name")`.
- Facts enter either by `instance name of "Entity" { field: expr, ... }` source text or by `Graph::add_entity_instance`.
- `add_entity_instance` enforces required fields, unknown-field rejection, and types against the entity contract. A fact that is missing is only possible for fields declared `optional`; the Evidence model had to use `retention_days: int optional` for case c.
- Policies reach facts through `entity_instances [of "Type"]`. They do not use relations or flows for instance-level joins. Joins are by field equality (for example `a.step_ref = s.step_id`).
- Suggested facts-file schema for WP-12: `{"instances":[{"entity":"Step","name":"s1","namespace":"wp10","fields":{...}}]}` mapped 1:1 to `Instance`. Alternative: accept a `.sea` fragment of `instance` declarations (already works).

## Requirements for WP-12

Smallest additive design:
1. Whole-policy tri-state needs no new code. WP-12 can call `Policy::evaluate` per policy today. It must not use `Graph::validate`, which loses the tri-state and skips operation-bound policies.
2. Per-binding results and bound instances do NOT exist. `Policy` gains a new public method in `policy/core.rs`:
   `pub fn evaluate_bindings(&self, graph:&Graph) -> Result<PolicyBindingReport,String>`, with `PolicyBindingReport{ result: ThreeValuedBool, support: usize, bindings: Vec<BindingResult> }` and `BindingResult{ variable, instance_id, instance_name, entity, result }`.
   - Implement it inside the quantifier arm at `core.rs:616`. That arm already computes each item's tri-state and only throws it away.
   - Evaluating each item with the same private code path keeps a single evaluator.
   - Nested quantifiers need a path (outer binding, then inner). Start with the outermost quantifier only.
   - Non-quantifier policies return an empty bindings list.
3. A caveat on the eager `expand()` at `core.rs:184` and `quantifier.rs:9`. It flattens quantifiers before the tri-state pass. A collection-level quantifier is evaluated per item only inside `evaluate_expression_three_valued`. Either skip `expand` for the top-level quantifier, or have `evaluate_bindings` call `get_collection` (needs to become `pub(crate)`-reachable from policy/core.rs; it already is within the crate).
4. Operation-bound policies. Add a thin `evaluate_operation_policies(doc: &ApplicationContractDocument, graph:&Graph, ctx:&ApplicationPolicyContext)` that, for each binding, looks up the policy and calls `evaluate_precondition`.
   - Facts for that path are the typed operation input, so the facts-file needs an `operations:[{operation, actor, input:{field:TypedValue}}]` section.
   - Its bound "instances" are the operation inputs, not graph instances.
   - Unbound or unevaluable expressions return `Error(String)`. Map that to `unknown` plus an error field.
   - Do not feed these policies to `Policy::evaluate`, which returns unknown for them.
5. CLI/JSON shape proposal: `[{policy_id, policy_name, kind, modality, binding:{variable,instance_id,entity,instance_name} | {operation, input} | null, result:"true"|"false"|"unknown", support:<n instances>, instances:[...]}]`. Emit one row per binding plus one policy-level summary row.
6. Keep `Violation` and `validate` unchanged for backward compatibility, and add `context` population only if the existing JSON consumers tolerate it.

## Risks

- Vacuous truth. A universal over zero instances returns True with no support count (case a). Real Constraint policies over an empty fact set will read as "satisfied". WP-12 must expose `support` (the instance count) so callers can distinguish "vacuous" from "verified". `evaluate_bindings` should return `support=0` there.
- `exists_unique` expand (`quantifier.rs`) counts only literal-true items, so a Null item can make the eager path return False instead of Unknown. I did not test this. The three-valued path at `core.rs:616` handles it correctly.
- Unknown is reported with the same `Severity` as a violation and a bool `is_satisfied=false`. Consumers that read only `is_satisfied` conflate unknown with false.
- Two evaluators exist inside DomainForge (`Policy::evaluate` and `application::evaluate_precondition`). The brief allows only DomainForge's own evaluators, and both are DomainForge's. They differ in capability (the application one has no quantifiers), so a single policy cannot be evaluated by both.
- `Instance.fields` is a HashMap. The collection builder sorts fields, so output is deterministic, but `fields()` iteration is not.
- A `.sea` model with `instance` declarations is resolved before evaluation, so the facts file must also be type-checked. An entity instance that violates its contract is rejected at add time, which means a "violating fact" in the sense of a type error cannot be evaluated; only a policy violation can.
