GodSpeed: an environment for a "forward-deployed engineer"

A plain-words report on the FDE convergence work, updated 2026-11-19. It explains what was built, what the checks have shown, and what still needs work. Running checks are described as they stood at this update.

1. What the project is

A forward-deployed engineer (FDE) is an engineer who works inside a customer's problem, not far away at head office. They study the situation, make a plan, try it, and report what really happened.

GodSpeed is a workplace for that job. It is not one program. It is five projects that were joined so they act as one:

  • SEA-Forge keeps the official records of each job (a "Field Case") and decides what is allowed.
  • Cognate Workbench is the screen a person works in. It also runs agents (AI helpers) safely.
  • Horizon shows a read-only view of the evidence, and will hold the phone-confirmation step.
  • Gauntlet runs things inside a safe box and is packaged for real computers.
  • DomainForge holds the written rules ("the model of the world") and can check them.

The one rule behind all of it: say what you expect before you try, then compare with what really happened. The records keep that order honest.

3. What is proven, and how

"Proven" here means a check ran and a record of it exists. It does not mean "bug-free".

Readiness run
One script builds the pinned version of every repo and runs 30 checks. It reached 30 of 30 on 2026-11-13 and again on 2026-11-15 at DomainForge 0.22.0 (an earlier 2026-11-15 run was 29 of 30; the cause was a test setup mistake, not a product bug). A later gate, Q01, checks that each platform has a recorded install test. STATUS says the full script has not been rerun since Q01 was added.
Tests
Examples: SEA-Forge server tests 640 passed, 0 failed at WP-21 part A. Horizon 1701 passed, 0 failed at the last recorded local run. Mutation checks: a test is run against a deliberately broken copy of the code, and it must fail. If it does not, the test is too weak. For WP-21B round 2, 11 of 11 such breakages were caught.
Real hardware
The owner ran install tests on a real Jetson (an ARM64 computer). The records are in the evidence folder.
Invariant
A rule that must be true every time, whatever happens. Example: "a closed case accepts no new work except the step that ends the plan."
Property test
Instead of writing a few examples, you state the invariant and let the computer invent thousands of random inputs, including nasty ones. If any input breaks the rule, the tool shrinks it to a small example, which then stays in the test suite for good. Tools: fast-check (TypeScript) and proptest (Rust).
Limits. The S1 result covers one kind of work, once. Nine S1 rows are only PARTIAL. Some predictions were wrong and were reported, not edited. Hosted-runner macOS GUI install is NOT_RUN. Upgrade tests were NOT_RUN for the first Horizon release because no earlier release existed.

4. The lesson: fix the cause, not the symptom

Two big changes (the Workbench capability runtime, and the Field Case record writer) went through many rounds of blind review by another AI model (Codex: 6 rounds on one, 4 on the other). Each round found new bugs. Each fix closed one bug, and the next round found a sibling of it. That is "whack-a-mole".

The owner said: look for the cause that produces the whole family. The review found one shared cause: the code was tested with examples, not with stated invariants. The fixes are changes of design that rule out whole classes:

  • Typed records. A record cannot hold free text from an untrusted server, so such text cannot leak into logs.
  • One boundary. Untrusted data is size-limited and checked once, at the door.
  • Facts only from our own state. The code does not guess (for example which request an oversized message belongs to). Guessing rules did not converge; simple rules did.
  • One write door. In the case store, every write needs a permit from one function, so an unchecked write does not compile.
  • Judge the result. Apply the whole change in memory and check the invariants on the outcome, not event by event.
  • Fail closed. If we cannot prove something is safe, we refuse.

Also: after three rounds, stop and derive the problem classes. Write invariants and generated tests first and show them failing before the fix. Source: root-cause-classes-2026-11-17.md. This lesson is being applied now, so its payoff is not yet proven: the invariant reviews are still running.

5. How we kept finding bugs, and what changed

For the two big changes, the work went round and round. We wrote code. Another AI model (Codex) reviewed it blind and found bugs. We fixed them and sent the code back. Each round found a sibling of the bug before, so the count did not drop fast.

The change: after about three rounds, we stop fixing single bugs. We find the rule that all of them break, write it as a test that must always hold, and watch that test fail first. Then we change the design so that whole family cannot happen.

Example: the Workbench capability runtime (T3, PR #39). It took 10 review rounds. Early rounds found separate holes, such as a process slot released while its process group was still alive, and gaps in scrubbing short secrets. Later rounds found that guessing rules did not converge, so the fixes moved to rules that need no guessing. When it merged (squash efdcc1c), we wrote the limits down instead of hiding them:

  • Tool results are stored in the conversation on purpose.
  • A rare crash window is still open. It waits for a Linux "cgroup" follow-up.

The runtime ships switched off by default.

Glossary

Agent
An AI helper that can take steps on a computer.
CI
Automatic checks that run when code is proposed.
Contract
A written, checkable agreement on the shape of data passed between two programs.
Field Case
The official record of one job, kept by SEA-Forge.
Fail closed
When unsure, say no.
Gate
A check that must pass before work moves on.
MCP
A standard way for an AI app to talk to outside tools.
Mutation check
Break the code on purpose and see if the tests notice.
Passkey
A login method where your phone proves it is you, with no password.
PR (pull request)
A proposed code change that others review before it joins main.
Qualified
An install was tested on that system and a record was kept.
Whack-a-mole
Fixing one bug at a time while the same kind keeps appearing.
