## Corrections applied during execution

Three items in the block above did not survive contact with the repository.
Each is corrected here with the evidence, per the authority order (canonical
spec > work packet).

1. **The reload event is `invalid_reload_error`, not `config.reload_failed`.**
   `.agents/specs/spec-full.md` §8.4 names it: "Invalid reload ⇒ keep
   last-known-good + operator-visible `invalid_reload_error` event." The packet's
   name appears nowhere in the spec. Implemented as `invalid_reload_error`.

2. **"Policy parse" is not a startup preflight, because this server has no
   startup policy.** The policy is per-request: `SubmitPayload.policy` /
   `AgentProbe.policy`, resolved against the root by
   `agent_probe::resolve_policy_path` (`agent_probe.rs:507`). `ServerConfig` has
   no policy field. Spec §8.3's blast-radius table agrees that this is not a
   startup concern: "policy errors block all new runs (server keeps in-flight
   runs); `server.yaml` errors block the server only." A parse failure already
   fails the run that named the policy.

3. **"Sandbox availability" is not a startup preflight either, for the same
   reason.** The sandbox class comes from the authority grant per request
   (`sea-forge-authority/src/lib.rs:1705`, defaulting to `local`), and the server
   dispatches on it at `delegation.rs:1206` — it never calls
   `sandbox_select`. Probing `jail` at startup and refusing to boot would break
   every cell that only ever uses `local`, which is the default. `jail`
   unavailability already denies the affected work with a typed
   `jail_unavailable` / `unsupported_sandbox_class_error`, which is what
   acceptance criterion 2 actually asks for and is pre-existing behaviour.

Also pre-existing and **not** rebuilt: socket-in-use already blocks startup with
a typed `AddrInUse` error (`lib.rs::lock_socket_path`, and SF-001 added the
`sun_path` length check ahead of it); `ServerConfig::load` already returns typed
errors for unreadable/malformed/invalid-agent files — only `main.rs` was
swallowing them; the DomainForge version guard already runs inside
`domainforge::load_validate`, which is where §8.3 requires it ("blocks the
affected plan before side effects"), so hoisting it to startup would add a
dependency for a check already correctly placed.

That leaves **`notify_command` argv0** as the one genuinely host-level,
genuinely blocking preflight in §8.5's list that was missing. It is implemented
(`lib.rs::check_notify_command`), and it matters precisely because the runtime
notify path deliberately swallows failures (§10.3) — correct for a transient
hook error, wrong for a hook that can never run at all.

Acceptance criterion 5 ("a concurrent status/read query succeeds while another
request is timing out") is covered structurally rather than by a dedicated test:
each connection gets its own task, and `dispatch_bounded` spawns the handler, so
a stalled request occupies neither the accept loop nor another connection. The
live test asserts the server still answers `system_hello` after a request times
out.

## Context

The server currently swallows configuration errors and discards reloads. A
silent default can change the cell root, socket path, or policy digest without
the operator knowing. The lack of a request timeout means one long case commit
can starve inspection and recovery.

## Required outcome

Startup, reload, and request handling all fail closed with typed, recoverable
errors. No invalid configuration produces a running server under unintended
defaults.

## Current evidence

- `main.rs:24-30` — `unwrap_or_else` falls back to `ServerConfig::default()`.
- `lib.rs:1455-1461` — `if let Ok(new_config) = state.reload_config() { let _ = new_config; }`.
- Connection handler (in `lib.rs` `run`/`serve`) — no `tokio::time::timeout`
  around individual request handlers.

## Implementation boundaries

- Touch only `main.rs`, `config.rs`, `lib.rs`, and focused integration tests.
- Do not weaken sandbox fallback or change policy evaluation semantics.
- Preserve the first-run case (absent `server.yaml` is valid).

## Acceptance scenarios

1. Malformed YAML, invalid agent endpoint, non-existent sandbox, policy parse
   error, DomainForge version mismatch, and socket-in-use each produce a typed
   startup error and non-zero exit.
2. A valid `server.yaml` change followed by a protected request triggers a
   reload that affects the next dispatch.
3. An invalid reload retains the last-known-good config and publishes a typed
   `config.reload_failed` event.
4. A handler sleeping 15s returns a timeout response at 10s; the request's
   durable status is recoverable via `request.get_status`.

## Verification procedure

```sh
cargo test -p sea-forge-server -- --test-threads=1
cargo test -p sea-forge-server --test conformance_sfwp
```

## Integration notes

SF-008 (readiness slice) depends on preflight results being visible. SF-012
(packaged E2E) depends on startup failing safely. SF-006 (idempotency) depends
on the timeout preserving request status.

## Known traps

- Do not cancel the underlying work on timeout — return a timeout *response*
  and let the work complete in the background; only the *response* is timed out.
- Preserve test isolation: some tests start a server without a `server.yaml`;
  the absent-file path must remain `Ok(default)`.

## Definition of done

Every invalid-config and unavailable-preflight case blocks startup; reload is
atomic with a typed failure event; the 10s timeout preserves recoverable status.
