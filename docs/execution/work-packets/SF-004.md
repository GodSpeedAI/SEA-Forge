## Context

The case dispatch writes runs under `cases/<case>/runs/<run>`, but the run-view
projection reads only `<root>/runs/<run>`. A case-linked run is operationally
orphaned — the Workbench can list it but not open it.

## Required outcome

One run locator resolves both layouts. Existing flat runs remain readable. New
case-owned runs are inspectable from every surface.

## Current evidence

- `run_views.rs:365-367` — `run_dir` returns `root.join("runs").join(run_id)`.
- `case_dispatch.rs:513-518` — writes under `root/cases/<case>/runs/<run>`.

## Implementation boundaries

- Modify `run_views::run_dir` to probe both paths (flat first, then case-owned
  scan). This is a read-time fallback, not a dual-write.
- Do not touch `case_dispatch.rs` (owned by SF-003).
- Do not re-key or rewrite historical ledger entries.

## Acceptance scenarios

1. `run.get` for a CLI-created run (flat) → complete record.
2. `run.get` for a case-created run (case-owned) → complete record.
3. After server restart, both still resolve.
4. `case.get_horizon` run links all open.
5. `sea-forge migrate` relocates a flat run to case-owned without changing its
   ID or ledger hash.

## Verification procedure

```sh
cargo test -p sea-forge-server sfwp
cargo test -p sea-forge-cli migrate
devbox run -- just proof
```

## Integration notes

SF-009 (case-to-settled-run slice) depends on this locator. The Workbench
`RunRecordPage` links become live once this lands.

## Known traps

- The case-owned scan must validate `run_id` the same way `valid_run_id` does
  (alphanumeric + dash/underscore) to prevent path traversal.
- Do not assume a run is in only one layout — a migration in progress may leave
  a copy in both; prefer the case-owned one if both exist.

## Definition of done

Every run ID from any source resolves through one locator, before and after
restart, without re-keying history.
