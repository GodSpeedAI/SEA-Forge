## Corrections applied during execution

1. **`run_dir` still returns a path for a run that exists nowhere.** The
   pre-existing contract was "a valid id always yields a path; callers read
   through it and treat an unreadable file as absence." Making the locator
   return `None` for an absent run would have turned "no such run" into
   "malformed run id" at every call site and changed `run_get`'s error class
   for a case existing tests pin. The probe is therefore additive: flat, then
   case-owned, then the flat path as the unchanged fallback.

2. **`case_run_dir` scans `cases/*/runs/` rather than reading `case.json`'s
   `run_ids`.** A run directory exists from the moment its episode records the
   first governance event, which is before the case file naming it is
   rewritten. Resolving off `run_ids` would have made a run unreachable during
   exactly the window a crash can leave behind.

3. **A duplicated id needed a stated winner.** Nothing prevents the same id
   appearing in both layouts, and if `run_get` and `run_dirs` broke the tie
   differently a Workbench link and the list it came from would open different
   records. Flat wins in both: it is the older layout and the one the minimum
   CLI proofs read. `run_dirs` sorts the case directories before the merge so
   the result does not depend on `readdir` order.

4. **The migration test asserted the wrong half of "lossless".** It checked
   that each ledger entry *has* a `sha256`, which passes for a migration that
   hashes one file and moves another. It now recomputes the digest at the
   destination and compares, with a guard that at least one relocated run file
   was covered — the guard fired on the first run and caught a wrong path
   prefix in the check itself.

Adversarial check: with the case-owned probe neutralized in `run_dir` and
`run_dirs`, 4 of the 6 new tests fail. The 2 that still pass
(`a_duplicated_id_resolves_to_the_flat_layout`,
`the_case_owned_probe_does_not_widen_the_traversal_surface`) are guards — they
are meant to hold in both states, and a guard that only holds after the change
would not be a guard.

Deliberately **not** done:

- **The other flat-only readers were left alone.** `delegation.rs`,
  `agent_probe.rs`, `server/lib.rs`, `transcript_seal.rs`, and
  `swe_seed_reconciliation.rs` also build `<root>/runs/<id>` paths, but they
  read runs *they themselves wrote* in the flat layout. Routing them through
  the locator would widen the change without fixing a reachable defect, and
  they are outside this packet's `allowed_paths`.
- **Relocating flat runs is not required.** The packet says so explicitly —
  the locator is the deliverable. `sea-forge migrate` already relocates, and is
  unchanged apart from the strengthened test.

## Context

The case dispatch writes runs under `cases/<case>/runs/<run>`, but the run-view
projection reads only `<root>/runs/<run>`. A case-linked run is operationally
orphaned — the Workbench can list it but not open it.

## Required outcome

One run locator resolves both layouts. Existing flat runs remain readable. New
case-owned runs are inspectable from every surface.

## Current evidence

- `run_views.rs:365-367` — `run_dir` returns `root.join("runs").join(run_id)`.
- `case_dispatch.rs:513-518` — writes under `root/cases/<case>/runs/<run>`.

## Implementation boundaries

- Modify `run_views::run_dir` to probe both paths (flat first, then case-owned
  scan). This is a read-time fallback, not a dual-write.
- Do not touch `case_dispatch.rs` (owned by SF-003).
- Do not re-key or rewrite historical ledger entries.

## Acceptance scenarios

1. `run.get` for a CLI-created run (flat) → complete record.
2. `run.get` for a case-created run (case-owned) → complete record.
3. After server restart, both still resolve.
4. `case.get_horizon` run links all open.
5. `sea-forge migrate` relocates a flat run to case-owned without changing its
   ID or ledger hash.

## Verification procedure

```sh
cargo test -p sea-forge-server sfwp
cargo test -p sea-forge-cli migrate
devbox run -- just proof
```

## Integration notes

SF-009 (case-to-settled-run slice) depends on this locator. The Workbench

## Known traps

- The case-owned scan must validate `run_id` the same way `valid_run_id` does
  (alphanumeric + dash/underscore) to prevent path traversal.
- Do not assume a run is in only one layout — a migration in progress may leave
  a copy in both; prefer the case-owned one if both exist.

## Definition of done

Every run ID from any source resolves through one locator, before and after
restart, without re-keying history.
