## Context

The correlation store records request status (good for reconnect recovery) but
does not prevent re-execution. A retried mutation can create two cases. The UI
generates the request ID inside the actor, so if the invoke rejects, the ID is
lost and recovery is impossible.

## Required outcome

Server-enforced idempotency: a stable request ID with the same operation and
payload returns the stored terminal outcome; a changed payload is rejected. The
client generates and retains the ID before send.

## Current evidence

- `correlation.rs:81-93` — `record_pending` overwrites unconditionally.
- `caseAuthoringMachine.ts:101` — `const id = requestId()` inside the actor.

## Implementation boundaries

- `correlation.rs`: `record_pending` checks for an existing terminal record
  first; `record_outcome` stores a payload hash for dedupe.
- `lib.rs` dispatch: check dedupe before executing a command verb.
- `caseAuthoringMachine.ts`: move `requestId()` to context assignment before
  the commit actor invokes.
- Do not change the correlation file format (additive hash field).

## Acceptance scenarios

1. Commit succeeds but response is lost; client retries same ID+payload → same
   outcome, one case.
2. Same ID, different payload → `request_id_reused` rejection.
3. Server restart mid-pending → `request.get_status` returns terminal outcome.
4. UI disconnect during commit → recovers by stored ID.

## Integration notes

SF-009 and SF-010 rely on idempotent mutations for safe case and approval
flows. SF-002's timeout must preserve request status for this recovery to work.

## Known traps

- The payload hash must be stable across serialization (use canonical JSON or a
  deterministic hash of the serde_json::Value, not a Debug string).
- Existing request records from before this change have no payload hash; treat
  them as non-dedupeable (proceed normally).

## Definition of done

A dropped or ambiguous mutation recovers to exactly one outcome with the same
terminal response, across reconnect and restart.
