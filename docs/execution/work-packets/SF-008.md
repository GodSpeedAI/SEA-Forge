## Context

The opening experience of the Workbench is the first impression and the first
trust boundary. Today it shows fabricated constants. The server has the data
(self-model, Thoth, config) but does not surface it as a structured readiness
view.

## Required outcome

The Workbench opens to source-backed readiness with resolved identity, honest
status vocabulary, and actionable affordances — all fetched from the server.

## Current evidence

- `readiness.rs` — returns error on unconfigured install.
- `router.tsx:38-51` — fabricated `mockGuardContext`.
- `sea-forge-thoth` — governed `ask` with ledger chain.

## Implementation boundaries

- Extend `readiness.get` to return structured readiness for all states.
- Wire `useReadiness` to the server response.
- Separate declared vs demonstrated in the affordance answer.
- Do not implement unmapped catalog breadth (P-04).

## Acceptance scenarios

1. Empty cell → "uninitialized" + initialize action.
2. Healthy cell → identity, policy, model, sandbox, all green.
3. Blocked (no sandbox) → blocker + corrective action.
4. Affordance → declared vs demonstrated, source-linked.

## Verification procedure

```sh
cargo test -p sea-forge-server readiness
cargo test -p sea-forge-thoth
cd workbench && bun run check && bun run test
just workbench-check
```

## Integration notes

SF-009 (case slice) depends on readiness confirming the cell is healthy before
commit. SF-005 (identity) must land first so readiness shows resolved identity.

## Known traps

- Do not over-disclose: the affordance answer must respect disclosure controls
  (a capability not yet demonstrated must not render as available).
- The self-model seed is bundled and validated; use it, do not fabricate hashes.

## Definition of done

The first three journey steps work on a real stack with source-backed,
identity-aware, disclosure-controlled readiness.
