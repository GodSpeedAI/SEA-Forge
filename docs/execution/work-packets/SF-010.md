## Context

The journey's intervention and recovery steps require real approval
orchestration, disconnect-safe mutations, and restart-explicit orphans. The
building blocks exist (idempotency, durable events, approval records) but are
not wired through to a safe, observable Workbench experience.

## Required outcome

An approver acts with enforced SoD; an operator cancels, resumes, and recovers
interrupted work; orphaned work after restart is explicit and recoverable.

## Current evidence

- `approvals.rs` — `approval.list` and `approval.decide` implemented.
- `events.rs` — durable cursor and gap recovery exist.
- `delegation.rs` — delegation lifecycle with cancel exists.
- No disconnect-during-mutation or kill-during-delegation proof through the
  real stack.

## Implementation boundaries

- Wire approval inbox, operations, and delegation roster to real server state.
- Enforce SoD server-side in the approval decide path.
- Mark orphans explicitly on restart.
- Do not conflate cancellation with settlement.

## Acceptance scenarios

1. Expired approval → visible, non-actionable.
2. SoD violation → denial.
3. Disconnect during approval → recover by ID, one decision.
4. Kill during delegation → orphan on restart.
5. Cancel delegation → governance event.
6. Events resume after reconnect.

## Verification procedure

```sh
cargo test -p sea-forge-server approvals
cargo test -p sea-forge-server delegation
cd workbench && bun run check && bun run test
```

## Integration notes

SF-011 (evidence/reuse) depends on approval outcomes being complete and
auditable. SF-006 (idempotency) underpins disconnect recovery.

## Known traps

- Cancellation must record a governance event but must NOT produce a settlement
  (a cancelled delegation is not a settled run).
- Orphan marking must be idempotent across multiple restarts.

## Definition of done

The journey safely intervenes, cancels, approves, and recovers without losing
or duplicating governed state, with orphans explicit.
