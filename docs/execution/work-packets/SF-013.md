## Context

CI verifies the kernel but not the product halves. The release workflow claims
a crates.io install path that cannot resolve. The README describes a two-crate
system that no longer exists.

## Required outcome

Aggregate CI gates the full product. Release ships proven, checksummed
artifacts with honest notes. Documentation reflects reality.

## Current evidence

- `ci.yml` — no Workbench/package/E2E jobs.
- `release-please.yml:100-134` — publishes core + CLI only.
- `README.md:217-226`, `ARCHITECTURE.md:3` — stale two-crate narrative.

## Implementation boundaries

- CI/release changes require owner authorization.
- Refresh stale docs (S-01) in the same package.
- Do not publish to crates.io without full closure (R-10, S-10).

## Acceptance scenarios

1. CI aggregate requires all product halves.
2. Linux package + CLI archive checksummed.
3. Release notes accurate.
4. README/ARCHITECTURE reflect reality.
5. No hidden blocker.

## Verification procedure

```sh
devbox run -- just check
devbox run -- just test
just workbench-check
```

## Integration notes

This is the final gate. It depends on every prior packet producing green
evidence. The aggregate CI job is the mechanical enforcer of the completion
definition.

### Owner authorization required

CI workflow and release pipeline changes are explicitly ask-first under the
repository's safety boundaries. Package the change; apply only when authorized.

## Known traps

- Do not silently add `cargo install sea-forge-cli` back to the release notes.
- The aggregate CI job must fail the release if ANY product half is red.
- macOS E2E must pass before macOS is called "supported" in release notes.

## Definition of done

Aggregate CI gates the full product; release artifacts are checksummed and
proven; documentation is honest; the product-complete claim has no hidden
blocker.
